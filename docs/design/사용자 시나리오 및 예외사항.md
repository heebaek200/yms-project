# 사용자 시나리오 및 예외사항

> YMS의 주요 사용자가 서비스를 어떤 순서로 이용하는지와 각 단계에서 발생할 수 있는 예외 상황을 정리합니다.  
> 본 문서는 요구사항 문서를 실제 사용자 흐름으로 연결하기 위한 시나리오 문서입니다.

> **용어 기준:** 화면과 사용자 흐름에서는 협업 조직을 `제작팀`으로 표기하며, API·DB·소스 코드에서는 이에 대응하는 기술 식별자로 `Workspace`를 사용합니다.

## 1. 사용자 유형과 기본 전제

YMS에서는 사용자의 **전문 역할**, **제작팀 권한**, **프로젝트 권한**을 서로 구분합니다.

### 전문 역할

- CREATOR: 크리에이터
- PLANNER: 콘텐츠 기획자
- WRITER: 작가
- VIDEOGRAPHER: 촬영 담당
- EDITOR: 영상 편집자
- THUMBNAILER: 썸네일 디자이너

한 사용자는 여러 전문 역할을 동시에 가질 수 있습니다.

전문 역할은 전역 고정 목록이며 세부 업무는 제작팀별 작업 종류로 확장합니다. CREATOR를 포함한 모든 전문 역할은 담당자 검색과 업무 분류에 동일하게 사용하며 역할 자체로 별도 기능이나 재무 권한을 부여하지 않습니다.

### 제작팀 권한

- OWNER(소유자): 제작팀 전체 관리와 권한 변경
- ADMIN(관리자): 멤버 초대와 일반 멤버 제외, 채널, 프로젝트 그룹, 프로젝트와 재무 정보 관리
- MEMBER(멤버): 자신에게 허용된 프로젝트와 업무 기능 이용

### 프로젝트 권한

- EDIT: 프로젝트 조회 및 수정, 작업 관리 가능
- VIEW: 프로젝트 조회 및 채팅 가능, 프로젝트와 작업 수정 불가

CREATOR 역할을 가지고 있다는 이유만으로 제작팀 전체의 재무 정보가 자동으로 공개되지는 않습니다.

제작팀의 전체 비용, 수익, 손익과 ROI는 기본적으로 OWNER 또는 ADMIN만 조회할 수 있습니다.

## 2. 시나리오 1. 회원가입과 프로필 설정

### 주요 사용자

모든 사용자

### 정상 흐름

1. 사용자가 이메일, 비밀번호와 이름을 입력하여 회원가입합니다.
2. 사용자가 로그인합니다.
3. 최초 로그인 후 자신이 수행할 수 있는 전문 역할을 하나 이상 선택합니다.
4. 사용자가 프로필 설정을 저장합니다.
5. 시스템은 설정된 역할을 이후 작업자 검색과 기본 화면 구성에 활용합니다.

### 로그인 후 진입과 Workspace 복원 흐름

1. 시스템은 로그인 또는 저장된 인증 세션 복원 후 `profileSetupRequired`를 확인합니다.
2. 프로필 설정이 필요하면 사용자를 SCR-02로 이동합니다.
3. 프로필 설정이 완료되었으면 참여 Workspace 목록을 조회합니다.
4. 현재 탭의 Workspace 또는 사용자별 마지막 Workspace가 목록에 존재하는지 검증합니다.
5. 유효한 Workspace가 있으면 해당 Workspace를 현재 탭의 작업 범위로 복원하고 Dashboard로 이동합니다.
6. 저장된 Workspace가 없거나 접근 권한이 없으면 자동으로 다른 Workspace를 선택하지 않고 SCR-03으로 이동합니다.

보호 URL에서 로그인을 시작했더라도 원래 URL로 복귀하지 않고 위 표준 흐름을 따릅니다. 존재하지 않는 URL은 인증 상태와 관계없이 404로 처리합니다.

같은 브라우저에서는 하나의 로그인 계정을 공유하지만 현재 Workspace는 탭별로 독립적으로 유지합니다. 한 탭에서 Workspace를 변경해도 이미 열린 다른 탭의 작업 범위는 변경되지 않으며, 가장 최근 선택은 다음 탭 또는 다음 방문의 복원 후보로 저장합니다.

### 예외 상황

#### EX-1.1. 전문 역할을 선택하지 않은 경우

사용자가 전문 역할을 하나도 선택하지 않은 상태에서는 프로필 설정을 완료할 수 없습니다.

화면에는 역할을 하나 이상 선택하도록 안내합니다.

#### EX-1.2. Workspace 목록 조회 실패

Workspace 목록 조회 실패를 참여 Workspace가 없는 상태로 간주하거나 SCR-03으로 자동 이동하지 않습니다.

시스템은 조회 시작 즉시 애니메이션과 진행 문구를 표시합니다. 실패 시 전용 오류 상태와 재시도 동작을 제공하며, 재시도 중에도 사용자가 처리가 진행 중임을 알 수 있도록 버튼과 문구 상태를 변경합니다. 빠른 응답에 인위적인 대기 시간은 추가하지 않습니다.

#### EX-1.3. 저장된 Workspace 접근 권한 상실

저장된 Workspace가 현재 참여 목록에 없으면 해당 저장값을 폐기하고 SCR-03으로 이동합니다. 다른 Workspace를 자동으로 선택하지 않습니다.

같은 Workspace를 사용하는 다른 탭에도 무효 상태를 전파하여 SCR-03으로 이동시키되, 다른 유효한 Workspace를 사용하는 탭은 유지합니다.

#### EX-1.4. 여러 탭에서의 로그인과 Workspace 전환

로그인, 로그아웃과 인증 만료는 브라우저의 모든 탭에 공유합니다. 한 탭에서 로그아웃하면 모든 탭의 인증 상태와 탭별 현재 Workspace를 제거하지만 사용자별 마지막 Workspace ID는 다음 로그인을 위해 유지합니다.

일반적인 Workspace 전환은 현재 탭에만 적용합니다. 각 탭은 서로 다른 Workspace를 동시에 사용할 수 있으며, 새 탭은 사용자별 마지막 Workspace를 서버 목록으로 검증한 뒤 시작합니다.

#### EX-1.7. 기능을 사용하던 중 Workspace 전환

사용자가 목록 화면에서 Workspace를 전환하면 새 Workspace의 같은 기능 목록을 유지합니다.

상세 화면에서 전환한 경우 이전 Workspace의 리소스 ID와 선택 상태를 제거하고 새 Workspace의 같은 기능 목록으로 이동합니다. 새 Workspace에도 적용 가능한 검색과 필터는 가능한 범위에서 유지합니다.

화면에는 `{제작팀명} 제작팀으로 전환했습니다.`라는 정보성 안내만 표시합니다. 전환 과정에서 이전 리소스를 찾을 수 없게 되었거나 역할이 달라졌다는 설명을 전환 메시지에 포함하지 않습니다.

새 Workspace에서 현재 기능을 사용할 수 없으면 다른 화면으로 자동 이동하지 않고 현재 Workspace 이름이 포함된 접근 불가 화면을 표시합니다. 같은 메뉴 위치에 역할별로 다른 기능이 있더라도 자동으로 대신 열지 않습니다. 예를 들어 제작팀 정산 관리 화면에서 MEMBER인 Workspace로 전환해도 내 정산 화면으로 자동 이동하지 않습니다.

#### EX-1.8. 현재 Workspace에서 사용할 수 없는 기능 직접 접근

사용자가 URL, 알림 또는 저장된 링크를 이용해 특정 기능에 접근했으나 현재 Workspace에서는 이용할 수 없는 경우 다음 상태를 표시합니다.

> **이 기능을 이용할 수 없어요**<br>
> 현재 선택된 제작팀은 ‘{제작팀명}’입니다.<br>
> 다른 제작팀에서 이용하려던 기능이라면 제작팀을 전환해 주세요.

사용자는 `제작팀 전환` 또는 `대시보드로 이동`을 선택할 수 있습니다. 화면을 사용하는 동안 역할이 변경되어 다음 API 요청이 403을 반환한 경우에도 같은 상태를 사용합니다.

다른 Workspace 소속 리소스를 열었거나 리소스 존재 여부를 공개할 수 없는 경우에는 `현재 제작팀에서는 이 항목을 찾을 수 없어요`라고 안내하고 현재 제작팀 이름을 표시합니다. 이때는 `제작팀 전환`과 해당 기능의 `목록으로 이동` 동작을 제공합니다.

## 3. 시나리오 2. 제작팀 생성과 멤버 초대

### 주요 사용자

OWNER, ADMIN, 초대받은 MEMBER

### 정상 흐름 A. 제작팀 생성

1. 사용자가 새 제작팀을 생성합니다.
2. 제작팀 이름과 기본 정보를 입력합니다.
3. 제작팀을 생성한 사용자는 자동으로 OWNER 권한을 가집니다.
4. OWNER는 멤버 관리 화면에서 함께 작업할 사용자를 이메일로 초대합니다.
5. 시스템은 초대를 대기 상태로 저장합니다.
6. 초대받은 사용자가 로그인 후 초대를 확인합니다.
7. 사용자가 초대를 수락하면 제작팀 MEMBER로 등록됩니다.

초대 시 제작팀 권한을 선택하지 않으며 모든 신규·재참여 사용자는 MEMBER로 참여합니다. OWNER가 필요할 때 참여 완료 후 별도로 승격합니다.

### 정상 흐름 B. 가입하지 않은 사용자 초대

1. OWNER 또는 ADMIN이 아직 가입하지 않은 이메일을 초대합니다.
2. 시스템은 해당 이메일에 대한 초대 정보를 대기 상태로 저장합니다.
3. 사용자가 해당 이메일로 회원가입합니다.
4. 로그인 후 대기 중인 제작팀 초대를 확인합니다.
5. 사용자가 초대를 수락하면 해당 제작팀에 참여합니다.

### 예외 상황

#### EX-2.1. 초대 거절

초대받은 사용자는 초대를 거절할 수 있습니다.

거절된 초대는 제작팀 멤버로 전환되지 않습니다.

#### EX-2.2. 초대 취소 후 수락 시도

OWNER 또는 ADMIN이 대기 중인 초대를 취소한 뒤 사용자가 해당 초대를 수락하려는 경우 참여할 수 없습니다.

시스템은 더 이상 유효하지 않은 초대임을 안내합니다.

#### EX-2.3. 만료된 초대 처리 시도

사용자가 초대 목록을 조회한 뒤 초대가 만료된 경우 수락하거나 거절할 수 없습니다.

시스템은 초대가 만료되었음을 안내하고 대기 중 초대 목록을 최신 상태로 갱신합니다.

#### EX-2.4. 이미 참여 중인 사용자 재초대

ACTIVE 상태로 참여 중인 사용자를 다시 초대할 수 없습니다.

중복 멤버가 생성되지 않도록 서버에서도 참여 상태를 검증합니다.

LEFT 또는 REMOVED 멤버는 다시 초대할 수 있습니다. 초대를 수락하면 기존 Workspace Member 행을 ACTIVE로 복구하고 제작팀 권한은 MEMBER로 초기화합니다. 이전에 다른 멤버에게 넘긴 프로젝트 소유권과 비활성화된 프로젝트 참여 상태는 자동으로 되돌리지 않습니다.

#### EX-2.5. 마지막 OWNER의 권한 제거

제작팀에는 최소 한 명의 OWNER가 존재해야 합니다.

마지막 OWNER가 권한을 변경하거나 제작팀을 떠나려고 하는 경우 다른 멤버에게 소유권을 이전하도록 안내합니다.

제작팀은 복수 OWNER를 허용합니다. OWNER만 다른 ACTIVE 멤버를 OWNER로 승격할 수 있고, 다른 ACTIVE OWNER가 있을 때만 자신의 권한을 ADMIN 또는 MEMBER로 낮출 수 있습니다.

OWNER 승격 또는 강등을 선택하고 저장하면 시스템은 즉시 적용하지 않고 전용 확인 단계를 표시합니다. 확인 화면에는 대상 멤버, 변경 전후 권한과 권한 변경의 영향을 표시하며, 요청자는 대상 멤버의 이메일을 직접 입력해야 최종 실행 버튼을 사용할 수 있습니다.

자기 자신을 OWNER에서 강등하는 경우에는 변경 후 다른 OWNER만 소유자 권한을 다시 부여할 수 있음을 추가로 경고합니다. 마지막 ACTIVE OWNER인지 여부와 요청자의 현재 권한은 이메일 확인 이후에도 서버가 최종 저장 시점에 다시 검증합니다.

현재 사용자가 마지막 ACTIVE OWNER라면 시스템은 기존 멤버 목록 조회에 ACTIVE·OWNER 필터를 적용해 이를 확인하고 ADMIN·MEMBER 선택지를 비활성화합니다. 상태가 바뀌어 이미 강등을 선택한 경우에도 이메일 확인 화면으로 이동하기 직전에 같은 조회를 다시 수행해 먼저 차단합니다. 조회 실패 시 안전하게 강등을 진행하지 않습니다.

OWNER가 다른 ACTIVE OWNER를 제작팀에서 제외하면 일반 멤버 제외 모달 대신 `소유자 → 제외됨`과 접근·관리 권한 상실 영향을 강조하는 확인 화면을 표시합니다. 요청자는 대상 OWNER의 이메일을 다시 입력해야 제외할 수 있으며, 서버는 요청자와 대상의 최신 권한을 최종 요청 시점에 다시 검증합니다.

자신을 MEMBER로 변경하면 현재 제작팀 관리 URL에서 접근 불가 화면을 표시합니다. 자기 자신을 제외하는 제작팀 나가기는 이 화면에서 제공하지 않습니다.

#### EX-2.6. ADMIN의 허용되지 않은 권한 조작

ADMIN은 멤버를 초대하고 일반 MEMBER를 제외할 수 있지만 OWNER·ADMIN의 권한을 변경하거나 제외할 수 없고 다른 사용자를 승격할 수도 없습니다.

서버는 화면의 버튼 노출 여부와 관계없이 요청 시점의 요청자 권한과 대상 멤버 권한을 다시 검증합니다.

#### EX-2.7. OWNER 계정 접근 불가

OWNER 계정 접근권을 잃은 경우 ADMIN에게 자동 승계하거나 Workspace 화면에서 우회 권한을 제공하지 않습니다.

사용자는 계정 복구 절차를 우선 사용하고 복구할 수 없으면 시스템 운영자에게 문의합니다.

#### EX-2.8. 프로젝트 소유자의 제작팀 제외 또는 탈퇴

논리 삭제되지 않은 프로젝트를 소유한 멤버를 제작팀에서 제외하거나 탈퇴시키려 하면 시스템은 위험 확인 단계 전에 소유 프로젝트 수와 이전 필요성을 안내합니다. 보관 프로젝트도 복구 가능한 업무 데이터이므로 이전 대상에 포함합니다.

> 이 멤버가 소유한 프로젝트가 {N}개 있습니다. 프로젝트 소유권을 다른 활동 중인 멤버에게 이전한 뒤 제작팀에서 제외해 주세요.

각 프로젝트에서 다른 ACTIVE EDIT 프로젝트 참여자에게 소유권을 이전한 후 제외·탈퇴를 다시 진행합니다. 적합한 참여자가 없다면 ACTIVE 제작팀 멤버를 해당 프로젝트의 EDIT 참여자로 먼저 추가해야 합니다. 보관 Project도 기존 ACTIVE EDIT 참여자가 있으면 보관을 유지한 채 소유권을 이전할 수 있고, 후보가 없을 때만 복원하여 참여자 추가 또는 권한 변경을 수행합니다. 논리 삭제 프로젝트는 당시 소유자를 이력으로 유지하고 이전을 요구하지 않습니다.

차단 화면에는 소유 Project를 활성·보관 상태로 구분하여 나열하고, 이전 가능한 ACTIVE EDIT 참여자 유무와 다음 작업을 함께 표시합니다. 활성 Project와 이전 후보가 있는 보관 Project에는 참여자 관리 또는 소유권 이전 바로가기를 제공하며 별도의 일괄 이전 API는 추가하지 않습니다.

서버는 최종 제외·탈퇴 시점에 소유 프로젝트를 다시 확인합니다. 성공하면 대상 멤버의 나머지 활성 프로젝트 참여를 비활성화하고 참여 종료 시각을 기록합니다. 동시 요청으로 소유 프로젝트가 남아 있으면 제외·탈퇴 전체를 취소합니다.

## 4. 시나리오 3. 채널 등록과 프로젝트 그룹 설정

### 주요 사용자

OWNER, ADMIN

### 정상 흐름 A. 채널 등록

1. OWNER 또는 ADMIN이 제작팀의 채널 관리 화면으로 이동합니다.
2. 필수값인 채널명을 입력합니다.
3. 필요한 경우 YouTube 채널 ID, URL, 설명과 롱폼·쇼츠 기본 조회수 1회당 예상 수익 단가를 입력합니다.
4. 단가를 입력하지 않은 항목은 0원으로 저장합니다.
5. 시스템은 채널을 `MANUAL` 상태로 제작팀에 등록합니다.
6. 이후 프로젝트 생성 시 등록된 채널을 선택할 수 있습니다.

초기 릴리스에서는 Google 계정 연동 없이 이름만으로 수동 등록이 가능해야 합니다. YouTube 채널 ID나 URL을 입력하더라도 실제 연동 절차를 완료하기 전에는 `CONNECTED`로 표시하지 않습니다.

Channel 기본 단가를 수정해도 이미 생성된 YouTubePublication의 적용 단가 스냅샷은 자동으로 바뀌지 않습니다.

### 정상 흐름 B. 프로젝트 그룹 생성

1. OWNER 또는 ADMIN이 프로젝트 메뉴의 프로젝트 그룹 탭으로 이동합니다.
2. 새 프로젝트 그룹을 선택합니다.
3. 필수값인 프로젝트 그룹명과 선택값인 설명, 시작일과 종료일을 입력합니다.
4. 필요한 경우 생성 과정에서 아직 그룹이 없는 프로젝트를 선택합니다.
5. 선택한 프로젝트가 대표인 VideoContent에 동기화된 성과가 있으면 콘텐츠 성과가 새 그룹에 집계된다는 점을 확인합니다.
6. 시스템은 프로젝트 그룹을 PLANNING 상태로 저장하고 선택한 프로젝트를 함께 연결합니다.
7. 이후 프로젝트를 생성하거나 수정할 때도 해당 프로젝트 그룹을 선택적으로 연결할 수 있습니다.

프로젝트 그룹은 제작팀에 속하며 특정 채널을 직접 소유하지 않습니다.

### 정상 흐름 C. 프로젝트 그룹 외부 수익 등록

1. OWNER 또는 ADMIN이 프로젝트 그룹 상세 화면을 조회합니다.
2. `수익 등록`을 선택합니다.
3. 협찬, 제휴, 상품 판매 등 수익 유형과 실제로 발생했거나 금액이 확정된 금액, 기준일과 메모를 입력합니다.
4. 귀속 대상은 현재 프로젝트 그룹으로 고정되어 있으며 사용자가 다른 대상으로 변경할 수 없습니다.
5. 시스템은 공통 Revenue 서비스를 통해 실제 수익을 저장합니다.
6. 프로젝트 그룹의 실제 수익, 손익과 ROI 요약을 다시 계산합니다.

계약 예정액, 입금 상태, 미수금과 세금계산서는 관리하지 않습니다. 조회수 기반 예상 YouTube 수익도 프로젝트 그룹 실제 수익에 포함하지 않습니다.

### 예외 상황

#### EX-3.1. 다른 제작팀의 채널 접근

사용자가 현재 제작팀에 속하지 않은 채널 ID를 직접 요청에 포함하여 프로젝트에 연결하려는 경우 서버에서 차단합니다.

#### EX-3.2. 프로젝트 그룹 없이 프로젝트 생성

프로젝트 그룹은 선택 사항입니다.

일반 브이로그, 자체 기획 영상 등 별도의 프로젝트 그룹이 필요하지 않은 프로젝트는 프로젝트 그룹 없이 정상적으로 생성할 수 있어야 합니다.

#### EX-3.3. 하나의 프로젝트를 두 프로젝트 그룹에 연결

하나의 프로젝트는 최대 하나의 프로젝트 그룹에만 속할 수 있습니다.

프로젝트 그룹 생성과 함께 연결하거나 기존 그룹에 추가하고, 다른 프로젝트 그룹으로 옮기거나 연결을 해제할 때 해당 프로젝트가 대표인 VideoContent의 동기화된 성과 또는 계산 가능한 예상 플랫폼 수익이 존재하면 콘텐츠 성과의 집계 대상도 변경된다는 점을 확인해야 합니다. 다른 그룹으로 옮기거나 연결을 해제하는 Project에 작업자 지급 금액이나 직접 비용·수익도 있으면 실제 재무와 참고용 콘텐츠 성과의 이동 여부를 구분해 안내하며 영향 데이터가 없으면 확인 없이 저장합니다.

승인하면 프로젝트와 프로젝트 직접 비용·수익은 새 그룹의 집계에 반영됩니다. 프로젝트 그룹에 직접 등록된 비용과 수익은 원래 그룹에 남습니다.

서버는 여러 프로젝트의 유효성과 성과 이동 확인값을 모두 검사한 후 그룹 생성과 연결을 반영합니다. 하나라도 실패하거나 사용자가 확인을 취소하면 새 그룹이나 일부 연결만 남기지 않습니다.

#### EX-3.4. 서로 다른 채널의 프로젝트를 하나의 프로젝트 그룹에 포함

프로젝트 그룹은 특정 채널에 귀속되지 않으므로 하나의 프로젝트 그룹에 서로 다른 채널의 프로젝트를 포함할 수 있습니다.

이는 예외가 아니라 정상적인 사용 사례로 처리합니다.

#### EX-3.5. 사용 중인 프로젝트 그룹 삭제

프로젝트가 하나 이상 연결되어 있거나 프로젝트 그룹에 직접 귀속된 Expense 또는 Revenue가 존재하면 삭제할 수 없습니다.

운영상 더 이상 사용하지 않는 프로젝트 그룹은 CANCELLED 또는 COMPLETED 상태로 변경하여 이력을 보존합니다.

삭제 요청 시 서버가 연결된 프로젝트와 비용·수익 데이터를 최종 확인합니다. 아무 이력도 없는 빈 프로젝트 그룹만 물리 삭제합니다.

#### EX-3.6. 완료 또는 취소된 프로젝트 그룹에 프로젝트 연결

COMPLETED 또는 CANCELLED 상태인 프로젝트 그룹에는 새 프로젝트를 연결할 수 없습니다.

다시 연결해야 하면 OWNER 또는 ADMIN이 먼저 그룹을 ACTIVE 상태로 변경합니다. 완료 또는 취소 상태에서도 뒤늦게 확정된 수익과 이미 발생한 비용은 등록하거나 정정할 수 있습니다.

#### EX-3.7. MEMBER의 프로젝트 그룹 접근

MEMBER에게는 프로젝트 그룹 탭과 관리 Route를 제공하지 않습니다.

MEMBER는 자신이 참여한 프로젝트에서 프로젝트 그룹 이름만 읽기 전용으로 확인하며 다른 연결 프로젝트, 설명과 재무 정보에는 접근할 수 없습니다.

#### EX-3.8. 프로젝트 그룹명 중복

같은 제작팀에서 앞뒤 공백을 제거하고 영문 대소문자를 구분하지 않았을 때 같은 이름이 존재하면 생성을 차단합니다. 완료 또는 취소된 프로젝트 그룹도 중복 검사에 포함합니다.

## 5. 시나리오 4. 프로젝트 생성과 작업 배정

### 주요 사용자

현재 제작팀의 ACTIVE 멤버

### 정상 흐름

1. 사용자가 새 영상 프로젝트를 생성합니다.
2. 필수 프로젝트 제목과 선택 기획 내용을 입력합니다.
3. 제작팀에 등록된 채널을 선택합니다.
4. 사용자가 OWNER 또는 ADMIN이면 필요한 경우 프로젝트 그룹을 선택합니다. MEMBER에게는 선택 필드를 제공하지 않습니다.
5. 영상 유형 LONG / SHORTS 중 하나를 명시적으로 선택합니다.
6. 초기 상태 PLANNING / EDITING 중 하나를 선택하며 기본값은 PLANNING입니다.
7. 필요한 경우 제작 마감일과 업로드 예정일을 입력합니다.
8. 프로젝트를 생성한 사용자는 프로젝트 소유자이자 EDIT 참여자가 됩니다. VideoContent, YouTubePublication과 적용 단가 스냅샷은 아직 생성하지 않습니다.
9. 프로젝트 소유자는 `참여자 추가`에서 현재 제작팀의 ACTIVE 멤버를 한 명 이상 선택하고 EDIT 또는 VIEW 중 하나의 공통 권한을 부여합니다.
10. 프로젝트에 가편집, 종합 편집, 자막, 썸네일 등의 세부 작업을 생성합니다.
11. 각 작업에 담당자, 작업 기간과 작업자 지급 금액을 입력합니다.
12. 저장된 작업은 담당자의 일정과 대시보드에 반영됩니다.
13. 담당자에게 새 작업이 배정되었다는 알림을 제공합니다.

두 일정은 모두 생략하거나 하나만 입력할 수 있으며 둘 다 있으면 제작 마감일이 업로드 예정일보다 늦을 수 없습니다. 기존 프로젝트 사후 등록을 위해 과거 날짜도 허용합니다.

### 예외 상황

#### EX-4.1. 프로젝트에 참여하지 않은 사용자에게 작업 배정

해당 프로젝트의 참여자가 아닌 사용자는 작업 담당자로 지정할 수 없습니다.

담당자 선택 목록에서는 ACTIVE EDIT 프로젝트 참여자만 표시하고 서버에서도 참여 상태와 권한을 검증합니다. VIEW 또는 참여 종료 사용자는 과거 담당 이력에는 남지만 새 담당자로 선택할 수 없습니다.

#### EX-4.2. 작업과 전문 역할 불일치

편집 관련 작업에 EDITOR 역할이 없는 사용자를 배정하려는 경우 경고 메시지를 표시합니다.

예:

> 해당 사용자는 영상 편집자 역할이 등록되어 있지 않습니다. 그래도 배정하시겠습니까?

전문 역할은 검색과 실수 방지를 위한 정보이며 실제 배정을 강제로 차단하지는 않습니다.

#### EX-4.3. 다른 제작팀의 프로젝트 그룹 연결

현재 프로젝트와 다른 제작팀에 속한 프로젝트 그룹은 연결할 수 없습니다.

#### EX-4.4. VIEW 권한 사용자의 수정 시도

VIEW 권한을 가진 사용자는 프로젝트와 작업 정보를 조회하고 채팅에 참여할 수 있지만 프로젝트 정보, 작업 배정과 작업 상태를 직접 수정할 수 없습니다.

화면에서는 수정 기능을 숨기거나 비활성화하고 서버에서도 권한을 재검증합니다.

#### EX-4.5. 올바르지 않은 작업 기간

작업 종료일이 시작일보다 빠른 경우 저장할 수 없습니다.

작업 종료일이 프로젝트의 제작 마감일 이후인 경우에는 실제 제작 일정에서 발생할 수 있는 상황이므로 저장 자체를 차단하지 않고 사용자에게 일정 초과 경고를 표시합니다.

날짜 검증은 클라이언트와 서버 양쪽에서 수행합니다.

#### EX-4.6. 프로젝트 참여자와 제작팀 초대 혼동

프로젝트 소유자는 현재 제작팀 멤버를 프로젝트에 직접 추가할 수 있지만 제작팀 밖 사용자를 초대할 수는 없습니다.

참여자 검색 결과가 없으면 `제작팀에 참여 중인 멤버만 추가할 수 있습니다. 새로운 멤버의 초대는 제작팀 관리자에게 요청해 주세요.`라고 안내합니다.

#### EX-4.7. 참여자 일괄 추가 중 후보 상태 변경

복수 참여자 추가 요청은 전체 성공 또는 전체 실패로 처리합니다. 요청 대상 중 이미 참여 중인 멤버, 다른 Workspace의 멤버 또는 더 이상 ACTIVE가 아닌 멤버가 하나라도 있으면 아무도 추가하지 않고 최신 후보 목록을 다시 표시합니다.

현재 참여 종료 상태이며 Workspace에서는 ACTIVE인 멤버는 일반 참여자 추가 화면과 `현재 참여 종료자` 영역의 `다시 참여`에서 선택할 수 있습니다. 기존 Project Member를 재사용하되 EDIT 또는 VIEW를 새로 선택하고 이전 권한은 자동 복구하지 않습니다. Workspace에서 탈퇴했거나 제외된 멤버는 후보와 `다시 참여` 동작에서 제외하고, 카드에 현재 Workspace 상태와 `다시 초대한 후 참여시킬 수 있습니다.` 안내를 표시합니다.

EDIT로 재참여하면 여전히 같은 Project Member가 담당자인 미완료 Task의 담당 자격이 자동 회복됩니다. 재참여 확인 화면은 회복되는 미완료 Task 수를 표시합니다. 이미 다른 담당자로 변경된 Task는 되돌리지 않고 완료 Task의 담당 이력도 변경하지 않습니다. VIEW 재참여 시에는 `권한 부족 · 담당자 재지정 필요` 상태가 유지됩니다.

#### EX-4.8. 권한 강등 또는 참여 종료와 미완료 작업

EDIT 참여자를 VIEW로 변경하거나 프로젝트에서 제외해도 이미 배정된 Task의 담당자 참조와 이력은 삭제하지 않습니다. 미완료 Task에는 각각 `권한 부족 · 담당자 재지정 필요` 또는 `참여 종료 · 담당자 재지정 필요`를 표시하고 프로젝트 소유자나 관리자가 새 ACTIVE EDIT 담당자를 지정하도록 안내합니다.

EDIT에서 VIEW로 변경할 때는 영향 확인창을 표시합니다. 참여자 제외 확인창에는 대상 이름, 현재 권한과 미완료 담당 작업 수를 표시하며, 자신을 제외하는 Workspace OWNER·ADMIN에게는 프로젝트 채팅 참여가 종료되지만 Workspace 관리 접근은 유지된다는 점도 안내합니다.

#### EX-4.9. 프로젝트 소유권 이전

프로젝트 소유자 또는 Workspace OWNER·ADMIN은 같은 프로젝트의 다른 ACTIVE EDIT 참여자에게만 소유권을 이전할 수 있습니다. 대상이 VIEW이거나 프로젝트에 참여하지 않았다면 권한 변경 또는 참여자 추가를 먼저 완료합니다.

이전 확인창에는 대상 이름·복사 가능한 이메일과 기존 소유자가 EDIT 참여자로 남는다는 영향을 표시합니다. 사용자가 대상 이메일을 정확히 입력해야 최종 실행 버튼을 활성화합니다. Workspace OWNER·ADMIN은 이전 후에도 관리 권한으로 소유권을 다시 변경할 수 있다고 안내하고, 일반 Project Owner에게는 새 소유자 또는 Workspace 관리자의 협조가 필요하다고 안내합니다.

권한 변경, 참여 제외·재참여, 소유권 이전과 Workspace 멤버 제외·탈퇴가 동시에 요청되면 Workspace 단위로 순서대로 처리합니다. 각 요청은 잠금 이후 최신 상태를 다시 검증하며 저장 직전에 현재 Owner가 ACTIVE EDIT Project Member인지 확인합니다. 먼저 완료된 요청 때문에 조건이 달라졌다면 뒤 요청은 최신 상태 충돌로 실패하고 화면은 참여자 목록을 다시 조회합니다.

#### EX-4.10. 보관 프로젝트의 참여자 변경

보관된 프로젝트의 참여자 관리 화면은 기본적으로 조회 전용입니다. 참여자 추가·재참여·권한 변경·제외는 비활성화하지만, 기존 ACTIVE EDIT 참여자에게 소유권을 이전하는 기능은 제공합니다. 이전 후보가 없다면 프로젝트를 복원하고 EDIT 참여자를 확보한 뒤 이전합니다. 소유권 이전만 수행한 경우 프로젝트는 보관 상태를 유지합니다.

#### EX-4.11. Project Member 감사 이력

Project Owner와 Workspace OWNER·ADMIN은 참여자 카드의 `변경 이력`에서 최초 참여, 재참여, 권한 변경, 참여 종료와 관련 소유권 이전을 시간순으로 확인할 수 있습니다. 일반 EDIT·VIEW 참여자에게는 이력 액션과 감사 데이터를 제공하지 않습니다.

기존 Project Member에는 SYSTEM 처리자가 현재 참여 정보를 기준으로 만든 초기 이력을 표시합니다. 알 수 없는 과거 권한 변경이나 재참여는 추정하지 않습니다.

#### EX-4.12. Project Channel 또는 기본 영상 유형 변경

Project의 Channel과 기본 영상 유형은 이후 생성할 VideoContent와 YouTubePublication의 초기값입니다. Project 값을 변경해도 기존 결과물, 게시 Channel과 적용 단가를 자동 변경하지 않습니다.

기존 YouTubePublication의 Channel 또는 VideoContent 영상 유형을 변경하면서 DEFAULT 수익 방식을 유지하면 새 기본 단가로 바뀐다는 점을 저장 전에 안내하고 같은 요청에서 새 단가를 스냅샷합니다. CUSTOM과 DISABLED 설정은 유지합니다.

## 6. 시나리오 5. 작업 수행과 프로젝트 협업

### 주요 사용자

EDITOR, THUMBNAILER, 기타 작업자, CREATOR

### 정상 흐름

1. 작업자가 로그인합니다.
2. 대시보드 상단에서 현재 제작팀을 확인하고 자신에게 배정된 마감 예정 작업과 알림을 확인합니다.
3. 작업 일정 또는 오늘 마감 항목을 선택하여 현재 제작팀의 프로젝트 상세 화면으로 이동합니다. Task 상세 UI가 구현되기 전에는 프로젝트 상세까지만 이동합니다.
4. 프로젝트 채팅에서 크리에이터 및 다른 참여자와 메시지를 주고받습니다.
5. 작업을 시작하면 상태를 진행 중으로 변경합니다.
6. 작업 중 요청이나 피드백을 채팅으로 확인합니다.
7. 작업이 끝나면 상태를 검수 요청으로 변경합니다.
8. 프로젝트 소유자 또는 권한이 있는 사용자가 결과물을 확인합니다.
9. 수정이 필요한 경우 작업을 반려하여 진행 중 상태로 되돌리고 피드백을 전달합니다.
10. 작업자는 수정 후 다시 검수 요청을 할 수 있습니다.
11. 검수가 완료되면 작업 상태를 완료로 변경합니다.
12. 작업자는 자신의 정산 예정 금액과 향후 정산 상태를 확인할 수 있습니다.

편집자와 썸네일 작업자의 기본 사용 흐름에서는 제작팀 전체의 매출, 이익과 ROI가 필요하지 않습니다.

모든 ACTIVE 제작팀 멤버는 대시보드의 `새 프로젝트`를 선택할 수 있습니다. 화면은 `/projects?create=true`로 이동하여 프로젝트 생성 모달을 열며, 새로고침해도 모달을 복원합니다. 사용자가 모달을 닫거나 생성에 성공하면 Query를 제거하여 다시 열리지 않게 합니다.

OWNER와 ADMIN은 제작팀 전체의 접근 가능한 일정을 확인하고 MEMBER는 자신이 참여한 Project와 Task 범위만 확인합니다. MEMBER가 URL Query나 화면 필터를 조작하더라도 API는 다른 프로젝트의 일정과 요약 정보를 반환하지 않습니다. `내 작업`은 허용된 범위 중 현재 사용자에게 배정된 Task만 남깁니다.

### 예외 상황

#### EX-5.1. 참여하지 않은 프로젝트 직접 접근

사용자가 주소창에 자신이 참여하지 않은 프로젝트 ID를 직접 입력할 수 있습니다.

서버는 프로젝트 참여 여부를 확인하고 권한이 없는 경우 403 Forbidden으로 처리합니다.

화면에서는 현재 제작팀 이름과 함께 접근할 수 없음을 안내하고 `제작팀 전환`과 `대시보드로 이동` 동작을 제공합니다. 자동으로 다른 화면으로 이동시키지 않습니다.

#### EX-5.2. 읽지 않은 채팅 메시지

사용자가 프로젝트 채팅을 확인하지 않은 동안 새 메시지가 도착한 경우 읽지 않은 메시지 수를 표시합니다.

채팅방을 확인하면 사용자별 마지막 확인 위치를 갱신합니다.

#### EX-5.3. 완료된 작업의 일반 수정

완료 상태의 작업을 다시 수정하거나 상태를 되돌려야 하는 경우 일반 작업자에게 무제한 수정 권한을 제공하지 않습니다.

프로젝트 소유자 또는 적절한 EDIT 권한 사용자가 업무 상황을 확인한 뒤 변경하도록 합니다.

#### EX-5.4. 재무 정보 접근

MEMBER인 편집자 또는 썸네일 작업자가 제작팀의 전체 수익, 비용, 손익 또는 ROI 화면에 직접 접근하려는 경우 권한을 확인하여 차단합니다.

자신의 작업자 지급 금액과 개인 정산 정보는 조회할 수 있습니다.

참여 프로젝트에 연결된 영상 결과물의 조회수, 좋아요와 댓글 같은 공개 성과는 조회할 수 있지만 Channel 기본 단가, YouTube 게시물 적용 단가와 예상 플랫폼 수익은 프로젝트 소유자 또는 EDIT 참여자여도 OWNER나 ADMIN이 아니면 제공하지 않습니다.

#### EX-5.5. Workspace 관리자의 비참여 프로젝트 접근

OWNER와 ADMIN은 Project Member로 자동 등록되지 않아도 같은 제작팀의 모든 프로젝트를 조회하고 관리할 수 있습니다.

관리 목적으로 상세를 조회했다는 이유만으로 프로젝트 채팅 읽음 상태를 만들거나 채팅 참여자로 처리하지 않습니다.

#### EX-5.6. 프로젝트 상태 되돌리기와 재개

프로젝트 상태는 업무 진행을 나타내는 표지이므로 권한이 있는 사용자는 이전 상태로 되돌리거나 CANCELLED 프로젝트를 재개할 수 있습니다. 시스템은 변경 전후 상태, 변경자와 시각을 이력으로 남깁니다.

보관된 프로젝트를 PLANNING, EDITING 또는 REVIEW로 변경하면 일반 목록에서 계속 찾을 수 있도록 보관을 자동 해제합니다.

#### EX-5.7. 프로젝트 보관과 삭제

UPLOADED 또는 CANCELLED 프로젝트만 보관할 수 있고 보관은 해제할 수 있습니다. 프로젝트 삭제는 확인 후 논리 삭제하며 일반 목록, 보관함, 일정, 검색과 콘텐츠 성과에서 제외합니다. 삭제할 Project가 VideoContent의 대표이고 다른 활성 연결 Project가 있으면 사용자가 결과물별 새 대표를 지정해야 합니다. 후보가 하나뿐이면 미리 선택하되 확인을 거치며, 대표 이전과 삭제를 하나의 트랜잭션으로 처리합니다.

다른 활성 연결 Project가 없으면 삭제를 허용하고 연결과 삭제된 역사적 대표를 보존합니다. 해당 VideoContent는 활성 Project·ProjectGroup 콘텐츠 성과 집계에서 제외하고 나중에 활성 Project를 연결해 대표로 지정하면 다시 포함합니다. 삭제된 프로젝트의 실제 Expense, Revenue와 확정 Settlement는 재무 합계에서 제거하지 않고 `삭제된 프로젝트 · {기존 프로젝트명}`으로 출처를 유지합니다. 조회수 기반 예상 수익은 콘텐츠 성과와 함께 제외합니다.

직접 접근이 차단된 경우 현재 제작팀 이름이 포함된 공통 접근 불가 화면을 표시합니다.

#### EX-5.8. 검수 반려

검수 요청된 작업에 수정이 필요한 경우 프로젝트 소유자 또는 적절한 EDIT 권한 사용자는 작업을 반려할 수 있습니다.

반려된 작업은 완료 처리하지 않고 진행 중 상태로 되돌리며, 작업자는 피드백을 확인한 뒤 수정하여 다시 검수를 요청합니다.

반려와 재검수가 반복되더라도 기존 작업을 새 작업으로 복제하지 않고 동일한 작업의 상태 흐름으로 관리합니다.

## 7. 시나리오 6. 비용과 실제 수익 관리

### 주요 사용자

OWNER, ADMIN

### 정상 흐름 A. 비용 등록

1. OWNER 또는 ADMIN이 비용 관리 화면으로 이동합니다.
2. 콘텐츠 제작 과정에서 발생한 비용을 등록합니다.
3. 비용 유형을 선택합니다.
4. 금액과 발생일을 입력합니다.
5. 비용의 귀속 대상을 하나 선택합니다.
   - 프로젝트
   - 프로젝트 그룹
   - 채널
   - 제작팀
6. 시스템은 해당 Expense를 선택한 대상에 직접 귀속하여 저장합니다.

예를 들어 특정 프로젝트의 스튜디오 대관료는 프로젝트 비용으로, 여러 프로젝트를 위한 프로젝트 그룹 공통 촬영비는 프로젝트 그룹 비용으로 등록할 수 있습니다.

### 정상 흐름 B. 실제 수익 등록

1. OWNER 또는 ADMIN이 수익 관리 화면으로 이동합니다.
2. 수익 유형을 선택합니다.
3. 실제 발생한 금액과 발생일 또는 정산 기준일을 입력합니다.
4. 수익의 귀속 대상을 하나 선택합니다.
   - 프로젝트
   - 프로젝트 그룹
   - 채널
   - 제작팀
5. 시스템은 Revenue를 선택한 대상에 직접 귀속하여 저장합니다.

예를 들어 특정 영상의 제휴 링크 수익은 프로젝트에, 여러 영상을 포함하는 브랜드 계약금은 프로젝트 그룹에 귀속할 수 있습니다.

프로젝트 그룹 상세에서 등록한 수익은 현재 프로젝트 그룹에 귀속하고, 전체 비용·수익 화면에서도 같은 Revenue를 조회, 수정하거나 무효 처리할 수 있습니다.

### 예외 상황

#### EX-6.1. 하나의 비용을 여러 대상에 동시 귀속

하나의 Expense를 프로젝트와 프로젝트 그룹 등에 동시에 직접 귀속할 수 없습니다.

저장 시 정확히 하나의 귀속 대상만 선택해야 합니다.

#### EX-6.2. 하나의 수익을 여러 대상에 동시 귀속

하나의 Revenue를 프로젝트와 프로젝트 그룹 등에 동시에 직접 귀속할 수 없습니다.

프로젝트 그룹 수익을 프로젝트별로 임의 분배하려면 별도의 명시적인 기능이 필요하며 초기 릴리스에서는 지원하지 않습니다.

#### EX-6.3. 작업자 지급액의 중복 비용 등록

작업에 설정된 작업자 지급 금액은 프로젝트 제작비에 자동 포함됩니다.

동일한 금액을 별도의 Expense로 다시 입력하여 이중 집계해서는 안 됩니다.

#### EX-6.4. 상위 단위 수익의 임의 배분

채널에 귀속된 멤버십 수익이나 제작팀 전체 수익을 특정 프로젝트 또는 프로젝트 그룹의 수익으로 자동 배분하지 않습니다.

원래 귀속된 단위에 그대로 보존합니다.

#### EX-6.5. 외부 수익 중복 입력

하나의 협찬금이나 제휴 수익을 프로젝트 그룹과 소속 프로젝트에 각각 새 Revenue로 등록하면 별개의 수익으로 합산됩니다.

등록 화면에서 중복 입력 주의를 안내하되 금액과 메모가 비슷하다는 이유로 시스템이 자동 차단하지는 않습니다. 하나의 Revenue는 정확히 하나의 귀속 대상만 가집니다.

## 8. 시나리오 7. 작업자 정산

### 주요 사용자

OWNER, ADMIN, EDITOR, THUMBNAILER

### 정상 흐름 A. 제작팀 정산 관리

1. OWNER 또는 ADMIN이 `/workspace/settlements`의 제작팀 정산 관리 화면에서 대상 기간을 선택합니다.
2. 시스템이 해당 기간의 작업자별 지급 대상 작업을 집계합니다.
3. 정산이 DRAFT 상태로 생성됩니다.
4. 관리자가 작업 목록과 지급 예정 금액을 확인합니다.
5. 이상이 없으면 정산을 CONFIRMED 상태로 변경합니다.
6. 시스템은 확정 시점의 작업과 지급 금액을 스냅샷으로 보존합니다.
7. 실제 지급이 끝나면 관리자가 PAID 상태로 변경합니다.

### 정상 흐름 B. 내 정산 확인

1. 작업자가 로그인합니다.
2. MEMBER가 `/my/settlements`의 내 정산 화면으로 이동합니다.
3. 정산 대상 작업과 확정 금액을 확인합니다.
4. 현재 상태가 DRAFT, CONFIRMED 또는 PAID인지 확인합니다.

작업자는 제작팀 전체 정산 금액이나 다른 작업자의 지급액을 조회하지 않습니다.

제작팀 정산 관리와 내 정산은 서로 다른 화면, Route와 조회 로직을 사용합니다. 헤더에서 같은 메뉴 위치를 사용하더라도 역할에 따라 메뉴 이름, 아이콘과 목적지를 다르게 제공하며 두 기능 사이를 자동 전환하지 않습니다.

### 예외 상황

#### EX-7.1. 취소된 프로젝트의 완료 작업

프로젝트가 취소되었더라도 이미 완료되어 지급 대상이 된 작업은 정산에 포함할 수 있습니다.

프로젝트 취소 자체를 이유로 작업자의 완료된 지급 항목을 자동 삭제하지 않습니다.

#### EX-7.2. 정산 확정 후 작업 단가 변경

정산이 CONFIRMED 상태가 된 이후 해당 작업의 지급 금액이 변경되더라도 확정된 정산 금액은 자동으로 바뀌지 않습니다.

확정 당시 스냅샷을 기준으로 유지합니다.

#### EX-7.3. PAID 정산 수정

PAID 상태의 정산은 일반적인 수정 기능으로 변경할 수 없습니다.

오류 정정이 필요한 경우 별도의 정정 절차를 설계합니다.

#### EX-7.4. 동일 작업의 중복 정산

이미 다른 정산에 포함된 작업이 다시 신규 정산에 포함되지 않도록 서버에서 중복 여부를 검증합니다.

#### EX-7.5. DRAFT 상태의 지급 금액 변경

정산이 DRAFT 상태인 동안 작업의 지급 금액이나 지급 대상이 변경된 경우 관리자는 최신 작업 정보를 기준으로 정산을 다시 계산할 수 있습니다.

CONFIRMED 상태로 변경되는 시점부터 정산 항목과 금액을 스냅샷으로 고정하며 이후 작업 정보 변경을 자동 반영하지 않습니다.

## 9. 시나리오 8. 영상 업로드와 콘텐츠 가치 분석

### 주요 사용자

OWNER, ADMIN, 프로젝트 소유자

### 정상 흐름 A. 영상 업로드와 데이터 연결

1. 프로젝트의 필요한 작업이 완료됩니다.
2. 프로젝트 소유자, EDIT 참여자 또는 Workspace 관리자가 완성된 VideoContent를 생성합니다. Project의 제목, 담당 Channel과 영상 유형은 초기값으로만 제안합니다.
3. 한 Project에서 여러 결과물이 나왔다면 VideoContent를 추가하고, 여러 Project의 결과를 합쳤다면 대상 Project를 같은 VideoContent에 연결합니다.
4. 사용자가 VideoContent에 업로드한 YouTube 영상의 URL 또는 영상 ID, 실제 Channel과 게시 일시를 입력합니다.
5. 시스템은 허용된 YouTube 호스트의 `watch`, `shorts`, `youtu.be` URL 또는 직접 입력한 11자리 ID만 정규화하고 같은 제작팀에 이미 등록된 게시물인지 확인한 뒤 YouTubePublication을 생성합니다.
6. 사용자가 프로젝트 상태를 별도로 UPLOADED로 변경합니다. 결과물·게시물 생성과 상태 변경은 서로 자동 실행하지 않습니다.
7. 사용자가 게시물의 성과 동기화를 실행하면 시스템이 조회수 등 콘텐츠 성과 데이터를 가져옵니다.
8. 게시물에 설정된 조회수 1회당 수익 단가를 이용하여 YouTube 플랫폼 예상 수익을 계산할 수 있습니다.
9. 일반 MEMBER에게는 조회수, 좋아요와 댓글을 표시하고 OWNER와 ADMIN에게만 적용 단가와 예상 수익을 함께 표시합니다.

조회수 1회당 수익 단가 기반 예상 수익은 실제 수익으로 확정된 값이 아니며 실제 ROI 계산에는 포함하지 않습니다.

### 정상 흐름 B. 프로젝트 재무 성과

1. 시스템이 프로젝트 작업에 연결된 작업자 지급 금액을 집계합니다.
2. 프로젝트에 직접 귀속된 Expense를 합산합니다.
3. 프로젝트에 직접 귀속된 실제 Revenue를 합산합니다.
4. 실제 비용과 실제 수익을 기준으로 손익을 계산합니다.
5. 실제 비용이 존재하는 경우 ROI와 수익/비용 배수를 계산합니다.
6. 조회수 등 콘텐츠 성과는 재무 지표와 별도로 함께 표시합니다.

기본 계산은 다음과 같습니다.

```text
손익 = 실제 수익 - 실제 비용

ROI = (실제 수익 - 실제 비용) ÷ 실제 비용 × 100

수익/비용 배수 = 실제 수익 ÷ 실제 비용
```

### 정상 흐름 C. 프로젝트 그룹 재무 성과

1. OWNER 또는 ADMIN이 프로젝트 그룹 상세 화면을 조회합니다.
2. 시스템이 프로젝트 그룹에 직접 귀속된 Expense를 집계합니다.
3. 프로젝트 그룹에 포함된 프로젝트의 작업자 지급 금액과 프로젝트 Expense를 집계합니다.
4. 프로젝트 그룹에 직접 귀속된 실제 Revenue를 집계합니다.
5. 프로젝트 그룹에 포함된 프로젝트의 실제 Revenue를 집계합니다.
6. 실제 비용과 실제 수익을 이용하여 프로젝트 그룹 손익과 ROI를 계산합니다.
7. 각 VideoContent의 대표 Project를 기준으로 현재 성과와 누적 게시 성과를 한 번만 집계하여 함께 표시합니다. ProjectGroup 화면에서는 누적을 주 지표, 현재를 보조 지표로 사용합니다.

채널 또는 제작팀에 귀속된 비용과 수익은 프로젝트 그룹에 자동 배분하지 않습니다.

### 예외 상황

#### EX-8.1. 존재하지 않는 YouTube 영상

사용자가 잘못된 URL 또는 영상 ID를 입력하고 외부 API에서도 영상을 확인할 수 없는 경우 YouTubePublication을 생성하지 않습니다.

화면에는 URL 또는 영상 ID를 다시 확인하도록 안내합니다.

외부 API 장애와 사용자의 잘못된 입력은 서로 다른 오류로 처리합니다.

#### EX-8.2. YouTube API 호출 실패

외부 API 장애, 영상 조회 실패 또는 할당량 제한으로 데이터를 갱신하지 못한 경우 기존에 저장된 마지막 성공 데이터와 게시물 생명주기를 유지합니다. 외부 응답만으로 게시물을 REMOVED로 자동 변경하지 않습니다.

사용자에게 `확인 필요`, 마지막 성공 시각, 마지막 시도 시각과 오류를 표시합니다. 한 번도 동기화에 성공하지 않은 게시물은 0이 아니라 `미집계`로 표시합니다.

#### EX-8.3. 실제 수익이 0원인 프로젝트

실제 수익이 0원인 프로젝트도 정상적인 분석 대상입니다.

제작비만 발생한 프로젝트는 손실 프로젝트로 표시할 수 있어야 합니다.

#### EX-8.4. 실제 비용이 0원인 경우

실제 비용이 0원인 프로젝트나 프로젝트 그룹에서는 ROI 계산의 분모가 0이 되므로 ROI를 계산하지 않습니다.

화면에는 ROI를 0%로 오해할 수 있는 값 대신 계산 불가 또는 해당 없음 상태로 표시합니다.

#### EX-8.5. 조회수 기반 예상 수익만 존재하는 경우

실제 Revenue가 없고 연결된 YouTubePublication의 조회수 1회당 수익 단가 기반 예상 수익만 존재하는 프로젝트에서는 예상 수익을 참고 정보로 표시합니다.

예상 수익을 실제 매출로 간주하여 ROI를 계산하지 않습니다.

#### EX-8.6. 프로젝트 그룹 수익과 프로젝트 수익의 중복 집계

프로젝트 그룹에 직접 등록한 협찬 수익과 프로젝트에 직접 등록한 수익은 서로 별개의 Revenue입니다.

하나의 수익 항목을 양쪽에 동시에 귀속하여 중복 집계할 수 없습니다.

#### EX-8.7. 동일 YouTube 영상의 중복 등록

하나의 YouTube Video ID는 같은 Workspace에서 하나의 YouTubePublication으로만 등록할 수 있습니다.

이미 등록된 영상 ID 또는 URL을 다시 등록하려는 경우 시스템은 중복 등록을 차단하고 기존 VideoContent와 게시물 정보를 안내합니다. 여러 Project에서 같은 게시물을 다루어야 한다면 중복 게시물을 만들지 않고 해당 Project를 기존 VideoContent에 연결합니다.

Project와 VideoContent의 다대다 연결과 별개로 성과 집계는 VideoContent의 대표 Project만 사용하여 조회수와 예상 수익의 중복 집계를 방지합니다.

#### EX-8.8. YouTube 게시물 비활성 및 이력 보존

사용자가 YouTube 게시물을 더 이상 운영하지 않기로 명시하면 물리 삭제하지 않고 `게시 종료(REMOVED)`로 변경합니다. 과거에는 유효했으나 외부 삭제나 운영 종료로 사용할 수 없으면 UNAVAILABLE, 잘못 연결했으면 INCORRECT 사유를 선택합니다. UNAVAILABLE의 마지막 성공 성과는 누적 게시 성과에 포함하고 INCORRECT는 현재·누적 집계에서 모두 제외합니다. 수동 입력 또는 연동으로 확인한 게시 일시와 기존 동기화 이력은 보존하며 Project 상태는 자동으로 변경하지 않습니다.

#### EX-8.9. 수정 후 YouTube 재업로드

노란 딱지, 저작권 문제 또는 내용 수정으로 같은 영상 결과물을 다시 업로드하면 기존 YouTubePublication의 Video ID를 새 값으로 덮어쓰지 않습니다. 같은 VideoContent와 Channel에 새 YouTubePublication을 추가할 때 사용자가 기존 CURRENT 게시물의 대체를 명시하면 기존 게시물을 `대체됨(SUPERSEDED)`으로 바꾸고 두 게시물의 성과 이력을 모두 보존합니다. 병행 게시라면 다른 Channel을 선택하며 Channel별 CURRENT는 하나만 허용합니다.

#### EX-8.10. 하나의 Project에서 여러 영상 제작

긴 촬영·편집 결과를 여러 편으로 분리하면 하나의 Project에 여러 VideoContent를 연결합니다. 각 결과물은 자체 영상 유형과 0개 이상의 YouTubePublication을 가질 수 있습니다.

#### EX-8.11. 여러 Project를 하나의 영상으로 합본

여러 Project의 결과를 한 편으로 합치면 하나의 VideoContent에 여러 Project를 연결하고 집계 기준 대표 Project를 하나 지정합니다. 모든 관련 Project 상세에서 결과물을 조회할 수 있지만 콘텐츠 성과와 예상 플랫폼 수익은 대표 Project 및 해당 ProjectGroup에만 한 번 집계합니다.

#### EX-8.12. 현재 성과와 누적 게시 성과

한 VideoContent에 CURRENT 5만 회, SUPERSEDED 10만 회 게시물이 있으면 현재 성과는 5만 회, 누적 게시 성과는 15만 회로 표시합니다. 조회수, 좋아요, 댓글과 예상 플랫폼 수익에 같은 포함 기준을 적용하되 예상 플랫폼 수익은 각 게시물의 적용 단가로 개별 계산한 뒤 합산합니다.

Project·VideoContent 목록에서는 현재 성과를 우선하고 프로젝트 상세에서는 두 값을 함께 제공합니다. ProjectGroup과 분석 화면에서는 누적 게시 성과를 우선하고 현재 성과를 보조로 제공합니다. 게시물 목록에서는 각 게시물 자체 성과를 표시합니다.

마지막 성공값의 시각이 서로 달라도 합산하되 COMPLETE / PARTIAL / UNAVAILABLE 상태, 포함·미집계 게시물 수와 마지막 성공 시각을 함께 표시합니다. 초기에는 성공값을 집계에서 제외하는 임의의 만료 기간을 두지 않습니다.

#### EX-8.13. 게시물 복원과 대체 관계

SUPERSEDED 또는 REMOVED 게시물을 사용자가 명시적으로 CURRENT로 복원할 수 있습니다. 같은 VideoContent와 Channel에 다른 CURRENT가 있으면 어떤 게시물을 대체할지 다시 확인합니다. 자신을 대체하거나 다른 Workspace·VideoContent·Channel 게시물을 대체하는 관계와 순환 관계는 차단합니다.

새 게시물 등록 시 대체 게시물 ID가 전달되면 같은 VideoContent와 Channel의 현재 CURRENT 게시물과 정확히 일치해야 합니다. CURRENT가 없거나 다른 게시물 ID를 지정한 요청은 새 게시물을 만들지 않고 거부합니다.

모든 상태·종료 사유·대체 관계 변경은 변경 전후 값, 관련 게시물, 변경자, 시각과 사유를 이력으로 남기고 Channel별 시간순 타임라인으로 표시합니다.

#### EX-8.14. 대표 Project 변경과 성과 귀속 이동

같은 ProjectGroup 안에서 대표를 바꾸거나 양쪽 모두 그룹이 없으면 현재·새 Project를 모두 관리할 수 있는 프로젝트 소유자, EDIT 참여자 또는 Workspace 관리자가 변경할 수 있습니다. 서로 다른 그룹 사이 또는 그룹 있음·없음 사이의 변경은 Workspace OWNER·ADMIN만 수행합니다.

대표 변경으로 동기화된 콘텐츠 성과나 계산 가능한 예상 플랫폼 수익이 다른 ProjectGroup으로 이동하면 저장 전에 영향을 확인합니다. 실제 Expense·Revenue·손익·ROI는 대표 변경으로 이동하지 않습니다. 이전·새 Project와 변경 당시 ProjectGroup, 사유, 변경자와 시각은 전용 이력으로 보존합니다.

## 10. 시나리오 간 주요 연결 관계

YMS의 사용자 흐름은 각 기능이 독립적으로 끝나는 구조가 아닙니다.

```text
회원가입 및 프로필 설정
        ↓
제작팀 생성 또는 초대 수락
        ↓
채널 등록
        ↓
프로젝트 그룹 생성(선택)
        ↓
프로젝트 생성
        ↓
프로젝트 참여자와 작업 배정
        ↓
작업 수행 · 채팅 · 검수
        ↓
작업 완료 및 작업자 정산
        ↓
영상 업로드 및 YouTube 데이터 연결
        ↓
Expense / Revenue 기록
        ↓
프로젝트 및 프로젝트 그룹 재무 성과 분석
```

프로젝트 참여 여부와 권한은 작업, 채팅과 수정 기능에 영향을 줍니다.

작업에 설정된 지급 금액은 작업자의 정산과 프로젝트 제작비 양쪽에 영향을 줍니다.

Expense와 Revenue의 귀속 대상은 프로젝트 및 프로젝트 그룹 재무 성과 집계 범위를 결정합니다.

프로젝트가 프로젝트 그룹에 속하지 않아도 독립적인 협업과 성과 분석이 가능해야 합니다.

## 11. 공통 예외 처리 원칙

### 11.1. 서버 권한 검증

화면에서 버튼이나 메뉴를 숨기는 것만으로 권한을 제어해서는 안 됩니다.

제작팀, 프로젝트, 재무 정보에 대한 모든 주요 요청은 서버에서 사용자의 권한을 다시 확인합니다.

### 11.2. 입력값 검증

클라이언트에서 기본적인 사용자 편의 검증을 수행하더라도 서버에서도 동일하게 데이터 유효성을 검증합니다.

### 11.3. 외부 API 오류 구분

YouTube API 사용 시 다음 상황을 구분합니다.

- 사용자가 입력한 영상 정보가 올바르지 않은 경우
- 외부 서비스에서 영상을 조회할 수 없는 경우
- 인증 또는 권한이 부족한 경우
- 외부 API 자체가 실패한 경우
- 할당량 제한으로 조회할 수 없는 경우

### 11.4. 금액 0원 처리

비용 또는 수익이 0원인 것은 오류 데이터로 간주하지 않습니다.

다만 0으로 나누는 ROI 등의 지표는 별도로 처리하여 화면 오류나 잘못된 수치가 표시되지 않도록 합니다.

### 11.5. 재무 정보와 협업 정보 분리

일반 작업자에게 필요한 작업 일정, 채팅, 검수와 개인 정산 정보는 계속 제공해야 합니다.

반면 제작팀 전체 비용, 수익, 손익과 ROI는 재무 정보 접근 권한이 있는 사용자에게만 제공합니다.

이 원칙을 통해 YMS는 **크리에이터와 편집자 간의 협업 서비스**라는 기본 가치를 유지하면서, 운영자에게는 **콘텐츠 제작에 투입한 비용으로부터 얼마의 가치를 만들었는지 관리하는 기능**을 함께 제공합니다.
