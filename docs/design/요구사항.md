# 요구사항

> YMS(YouTube Management System)의 기능 및 비기능 요구사항을 정의합니다.  
> 본 문서는 초기 블로그 설계를 현재 구현 상태와 실제 배포 가능한 SaaS 구조에 맞게 재정리한 문서입니다.

> **용어 기준:** 크리에이터와 편집자·썸네일러가 함께 일하는 조직은 사용자와 업무 문서에서 `제작팀`으로 표기합니다. 프로젝트 안의 세부 수행 단위는 사용자 화면에서 `작업`, 그 분류는 `작업 종류`로 표기합니다. API 경로, DB 테이블과 소스 코드의 기술 식별자는 기존 `Workspace` / `workspace`, `Task` / `task`와 `Task Type` / `taskType`을 유지합니다.

## 1. 프로젝트 개요

### 1.1. 배경

YMS는 유튜브 채널을 운영하면서 여러 영상 편집자와 썸네일 작업자를 관리하는 미디어 에이전시를 가상의 클라이언트로 설정하여 기획한 서비스입니다.

현재 영상 제작 업무에서 카카오톡, 노션, 구글 스프레드시트 등에 분산되어 관리되는 일정, 작업 배정, 커뮤니케이션, 제작비 정산과 콘텐츠 성과 데이터를 하나의 웹 시스템에서 통합 관리하는 것을 목표로 합니다.

### 1.2. 핵심 가치

YMS는 다음 두 가지 가치를 함께 제공합니다.

#### 협업 도구로서의 가치

크리에이터, 편집자, 썸네일 작업자 등 실제 제작 참여자가 하나의 서비스에서 프로젝트와 작업을 확인하고 일정, 진행 상태, 채팅, 알림과 정산 정보를 관리할 수 있도록 합니다.

편집자와 썸네일 작업자에게는 전체 사업의 수익 구조보다 **자신에게 배정된 작업을 수행하고 검수를 거쳐 정산받는 흐름**이 우선됩니다.

#### 콘텐츠 비즈니스 관리 도구로서의 가치

YMS의 비즈니스 관점 핵심 가치는 **콘텐츠 제작에 투입한 비용으로부터 얼마의 가치를 만들었는지 관리하는 것**입니다.

- 제작팀을 중심으로 채널과 참여자를 관리합니다.
- 여러 콘텐츠 프로젝트를 하나의 프로젝트 그룹으로 묶어 관리할 수 있습니다.
- 작업자 인건비뿐 아니라 촬영, 장비, 장소, 라이선스, 외주 등 제작에 발생한 비용을 기록합니다.
- YouTube 플랫폼 수익뿐 아니라 광고·협찬·제휴·상품 판매 등 다양한 실제 수익원을 기록합니다.
- 프로젝트와 프로젝트 그룹 단위로 실제 비용과 실제 수익을 비교하여 재무 성과를 분석합니다.
- 조회수, 좋아요 등 콘텐츠 반응 지표는 금전적 재무 성과와 구분하여 참고 지표로 제공합니다.

초기 릴리스 이후 실제 사용자를 받을 수 있는 서비스로 확장 가능한 구조를 지향합니다.

### 1.3. 역할과 권한 개념

YMS에서는 역할과 권한을 다음 세 가지 범위로 구분합니다.

| 구분 | 값 | 의미 |
| --- | --- | --- |
| 전문 역할 | CREATOR, PLANNER, WRITER, VIDEOGRAPHER, EDITOR, THUMBNAILER | 사용자가 수행할 수 있는 업무 |
| 제작팀 권한 | OWNER, ADMIN, MEMBER | 조직 또는 팀 안에서의 관리 권한 |
| 프로젝트 권한 | EDIT, VIEW | 특정 프로젝트에 대한 접근 권한 |

한 사용자는 여러 전문 역할을 동시에 가질 수 있으며 여러 제작팀에 서로 다른 권한으로 참여할 수 있습니다.

전문 역할은 사용자가 수행할 수 있는 업무를 나타낼 뿐, 제작팀의 재무 정보에 대한 접근 권한을 자동으로 부여하지 않습니다.

## 2. 회원과 프로필

### REQ-01-01. 회원가입 및 로그인

사용자는 이메일과 비밀번호를 이용하여 회원가입하고 로그인할 수 있어야 합니다.

인증에 성공한 사용자는 자신이 참여한 제작팀, 프로젝트, 일정과 알림 정보에 접근할 수 있습니다.

### REQ-01-02. 다중 전문 역할 지원

사용자는 다음 전문 역할을 하나 이상 선택할 수 있습니다.

- CREATOR: 크리에이터
- PLANNER: 콘텐츠 기획자
- WRITER: 작가
- VIDEOGRAPHER: 촬영 담당
- EDITOR: 영상 편집자
- THUMBNAILER: 썸네일 디자이너

한 사람이 여러 업무를 담당할 수 있으므로 복수 선택을 허용합니다.

전문 역할은 전역 고정 목록으로 관리하며 사용자가 역할을 생성·수정·삭제하지 않습니다. 세부 업무 종류는 Workspace별 Task Type으로 확장합니다.

### REQ-01-03. 프로필 및 역할 정보 관리

사용자는 회원가입 이후 프로필 설정 화면에서 이름 또는 닉네임과 전문 역할을 설정하고 수정할 수 있습니다.

작업 담당자를 선택할 때 전문 역할을 검색·필터 조건과 참고 정보로 사용할 수 있어야 합니다. 시스템은 작업 종류와 전문 역할의 적합성을 판정하거나 배정을 제한하지 않습니다.

### REQ-01-04. 전문 역할의 기능 중립성

CREATOR를 포함한 전문 역할은 사용자가 수행할 수 있는 업무와 담당자 검색·필터 조건만 나타냅니다. 특정 전문 역할을 선택했다는 이유만으로 별도 기능이나 제작팀 재무 정보 접근 권한을 부여하지 않습니다.

조회수 기반 예상 수익의 기본 단가는 개인 프로필이 아니라 제작팀의 Channel에 설정합니다.

## 3. 제작팀과 멤버

### REQ-02-01. 제작팀 생성

사용자는 하나 이상의 제작팀을 생성할 수 있습니다.

제작팀은 다양한 전문 역할의 사용자가 협업하는 조직을 나타내며 채널, 프로젝트 그룹, 프로젝트, 멤버, 비용, 수익과 정산 정보를 관리하는 최상위 업무 단위입니다.

제작팀을 생성한 사용자는 해당 제작팀의 OWNER 권한을 가집니다.

### REQ-02-02. 제작팀 권한

제작팀에는 다음 권한을 사용합니다.

- OWNER(소유자): 제작팀 전체 관리, 관리자 지정, 다른 사용자에게 소유자 권한 부여 및 삭제 가능
- ADMIN(관리자): 멤버 초대와 일반 멤버 제외, 채널, 프로젝트 그룹, 프로젝트와 재무 정보 등 주요 업무 정보 관리 가능
- MEMBER(멤버): 참여 중인 프로젝트와 자신에게 허용된 업무 기능 사용 가능

제작팀에는 복수 OWNER가 존재할 수 있지만 ACTIVE OWNER는 항상 최소 한 명이어야 합니다. OWNER만 다른 ACTIVE 멤버의 제작팀 권한을 변경할 수 있으며, ADMIN은 OWNER·ADMIN을 조작하거나 다른 사용자의 권한을 승격할 수 없습니다.

### REQ-02-03. 멤버 초대

OWNER 또는 ADMIN은 이메일을 이용하여 사용자를 제작팀에 초대할 수 있습니다.

초대에는 다음 상태를 관리합니다.

- 초대 대기
- 수락
- 거절
- 취소

이미 YMS 회원인 사용자는 로그인 후 초대를 확인하여 수락하거나 거절할 수 있어야 합니다.

아직 회원이 아닌 이메일을 초대한 경우 회원가입 후 해당 초대를 이어서 처리할 수 있도록 설계합니다.

OWNER 또는 ADMIN은 유효한 PENDING 초대를 취소할 수 있습니다. 재전송 전용 기능은 제공하지 않으며 다시 초대할 때는 이메일 초대 폼에서 새 초대를 생성합니다.

초대를 수락한 사용자는 항상 MEMBER 권한으로 참여합니다. ACTIVE 멤버와 동일한 이메일 또는 동일 이메일의 유효한 PENDING 초대가 있으면 새 초대를 차단하지만, LEFT 또는 REMOVED 멤버는 다시 초대할 수 있습니다. 재참여하더라도 이전에 이전된 프로젝트 소유권이나 비활성화된 프로젝트 참여 권한은 자동으로 복구하지 않습니다.

### REQ-02-04. 멤버 관리

OWNER 또는 ADMIN은 제작팀 멤버 목록과 각 멤버의 전문 역할 및 제작팀 권한을 확인하고 이름·이메일, 멤버 상태, 전문 역할과 제작팀 권한으로 검색·필터링할 수 있습니다.

OWNER는 다른 ACTIVE 멤버의 권한을 변경하고 다른 멤버를 제작팀에서 제외할 수 있습니다. ADMIN은 일반 MEMBER만 제작팀에서 제외할 수 있습니다. LEFT 또는 REMOVED 멤버는 이력으로만 표시하고 관리 액션을 제공하지 않습니다.

OWNER는 다른 ACTIVE OWNER가 있을 때만 자신의 권한을 ADMIN 또는 MEMBER로 낮출 수 있습니다. MEMBER로 변경하면 현재 제작팀 관리 화면은 접근 불가 상태를 표시합니다.

일반적인 ADMIN과 MEMBER 사이의 권한 변경은 한 번의 저장으로 처리하지만, OWNER로 승격하거나 OWNER에서 강등하는 변경은 별도의 2단계 확인을 거쳐야 합니다. 최종 확인 단계에는 변경 전후 권한과 영향을 표시하고 대상 멤버의 이메일을 다시 입력해야 실행할 수 있도록 합니다. 자기 자신을 OWNER에서 강등할 때는 다른 OWNER만 해당 권한을 복구할 수 있음을 추가로 안내합니다.

마지막 ACTIVE OWNER의 강등은 이메일 확인 단계에 진입하기 전에 차단합니다. 화면은 기존 멤버 목록 조회 기능으로 전체 ACTIVE OWNER 수를 확인해 강등 선택지를 비활성화하고 다른 멤버를 먼저 OWNER로 지정하도록 안내하며, 별도의 API 경로를 추가하지 않습니다. 조회 이후의 동시 변경 가능성에 대비해 최종 저장 API도 같은 규칙을 다시 검증합니다.

OWNER가 다른 ACTIVE OWNER를 제작팀에서 제외할 때도 일반 멤버 제외보다 강한 확인 단계를 사용합니다. 대상의 권한과 접근이 함께 중단됨을 안내하고 대상 OWNER의 이메일을 다시 입력해야 최종 제외를 실행할 수 있도록 합니다. ADMIN과 MEMBER 제외에는 기존 확인 모달을 유지합니다.

논리 삭제되지 않은 프로젝트를 하나라도 소유한 멤버는 제작팀에서 제외하거나 탈퇴할 수 없습니다. 보관 프로젝트도 소유권 이전 대상에 포함하고, 논리 삭제 프로젝트의 소유자는 당시 이력으로 유지하여 이전 의무에서 제외합니다. 멤버 목록에서 `ownedProjectCount`를 제공하여 위험 확인 단계 전에 차단하되, 서버는 최종 제외·탈퇴 요청 시 같은 조건을 트랜잭션 안에서 다시 검증합니다.

제작팀에서 제외되거나 탈퇴한 멤버의 활성 프로젝트 참여는 비활성화하고 참여 종료 시각을 기록합니다. LEFT 또는 REMOVED 멤버가 재참여해도 기존 프로젝트 참여와 소유권은 자동 복구하지 않습니다. 소유권 일괄 이전 API는 초기 범위에 추가하지 않고 각 프로젝트의 기존 소유권 이전 기능을 사용합니다.

사용자는 SCR-03 `/workspaces`의 제작팀 카드 보조 메뉴에서 해당 제작팀을 직접 탈퇴할 수 있습니다. 탈퇴는 일상적인 전환 동작과 분리하여 제공하며, 실행 전 제작팀 이름을 정확히 입력해야 합니다. 현재 선택한 제작팀을 탈퇴하면 현재 선택을 해제하고 SCR-03에 머물며 다른 제작팀을 자동 선택하지 않습니다. 현재 선택하지 않은 제작팀을 탈퇴하면 기존 작업 문맥을 유지합니다.

제외·탈퇴 사전 검증은 마지막 ACTIVE OWNER 여부, 비삭제 소유 Project, 종료될 ACTIVE Project 참여 수와 담당자 재지정이 필요한 미완료 Task 수를 한 번에 반환합니다. 차단 사유가 여러 개이면 모두 함께 안내하며, 소유 Project는 활성·보관 상태를 구분해 각 해결 화면으로 연결합니다. 사전 조회는 안내용이며 제외·탈퇴 API가 같은 불변식을 저장 직전에 다시 검증합니다.

현재 선택하지 않은 Workspace의 Project 해결 화면으로 이동할 때는 대상 Workspace 이름을 포함한 전환 동작을 사용자가 명시적으로 선택해야 합니다. 현재 탭에서 대상 Workspace를 선택한 뒤 Project 화면으로 이동하며, 뒤로가기로 SCR-03에 복귀해도 이전 Workspace를 자동 복원하지 않습니다. 일반 Workspace 전환과 마찬가지로 다른 탭의 선택에는 영향을 주지 않습니다. Project 해결 화면으로 이동하지 않고 현재 선택하지 않은 Workspace를 바로 탈퇴한 경우에는 기존 현재 Workspace를 유지합니다.

#18 Task 관리 구현 전 Mock의 미완료 담당 작업 수는 기존 Project Member 메타에 준비된 `incompleteTaskCount` 합계를 사용합니다. 이는 #53 영향 안내 시나리오를 검증하기 위한 샘플 값이며 실제 Task별 담당 관계를 보장하지 않습니다. #18 구현 후에는 `project_tasks.assignee_project_member_id`와 `status != COMPLETED` 조건의 실제 집계로 교체합니다.

OWNER 계정 접근권을 잃은 경우 ADMIN이 권한을 승계하지 않습니다. 사용자는 계정 복구를 우선하고 복구할 수 없으면 시스템 운영자에게 문의합니다.

### REQ-02-05. 역할별 정보 노출

YMS는 사용자의 역할과 업무 목적에 따라 필요한 정보만 우선적으로 제공해야 합니다.

OWNER와 ADMIN은 제작팀의 비용, 수익, 프로젝트 그룹 재무 성과와 정산 현황을 조회하고 관리할 수 있습니다.

일반 MEMBER인 편집자 또는 썸네일 작업자는 기본적으로 다음 정보를 중심으로 이용합니다.

- 자신이 참여한 프로젝트
- 자신에게 배정된 작업과 일정
- 작업 진행 상태와 검수 결과
- 프로젝트 채팅과 알림
- 자신에게 지급될 작업 금액과 정산 상태

프로젝트에 대한 EDIT 또는 VIEW 권한만으로 제작팀 전체의 수익, 비용, 이익 또는 ROI 정보가 자동으로 공개되어서는 안 됩니다.

Channel 기본 단가, YouTube 게시물의 수익 계산 방식과 적용 단가, 조회수 기반 예상 플랫폼 수익은 OWNER와 ADMIN에게만 제공합니다. 일반 MEMBER는 참여 프로젝트와 연결된 영상 결과물의 조회수·좋아요·댓글 등 공개 성과 지표는 확인할 수 있지만 프로젝트 소유자 또는 EDIT 참여자여도 단가와 예상 금액을 조회하거나 변경할 수 없습니다.

향후 별도의 재무 권한이 필요한 경우 제작팀 권한과 독립된 세부 권한으로 확장할 수 있습니다.

## 4. 채널 관리

### REQ-03-01. 제작팀별 채널 등록

제작팀에는 하나 이상의 YouTube 채널을 등록할 수 있습니다.

채널명은 필수로 관리합니다. YouTube 채널 ID, 채널 URL과 설명은 선택 정보이며, 입력하지 않아도 채널을 등록할 수 있습니다.

채널에는 다음 정보를 관리합니다.

- 채널명
- YouTube 채널 ID
- YouTube 채널 URL
- 채널 설명
- YouTube 연동 상태
- 롱폼 기본 조회수 1회당 예상 수익 단가
- 쇼츠 기본 조회수 1회당 예상 수익 단가

초기에는 YouTube 계정 연동 없이 이름만으로 채널 정보를 수동 등록할 수 있어야 합니다. 사용자가 YouTube 채널 ID나 URL을 참고 정보로 입력했더라도 실제 연동 절차를 완료하기 전에는 연동된 채널로 간주하지 않습니다.

OWNER와 ADMIN은 Channel 생성·수정 시 롱폼과 쇼츠 기본 단가를 선택적으로 입력할 수 있습니다. 입력하지 않은 항목은 각각 0원으로 저장하며, 단가는 0 이상이고 소수점 여섯째 자리까지 허용합니다. 단가 변경은 이후 `DEFAULT` 방식으로 생성·수정되는 YouTube 게시물에만 영향을 주며 기존 게시물의 적용 단가 스냅샷을 자동으로 변경하지 않습니다.

채널의 비활성화와 삭제는 별개의 기능으로 제공합니다. 삭제 요청 시 서버가 프로젝트와 채널 귀속 업무 데이터의 연결 여부를 최종 확인하며, 연결 이력이 없는 채널만 물리 삭제합니다. 기존 프로젝트나 업무 데이터에서 사용 중이면 삭제를 거부하고 더 이상 새 프로젝트에서 선택하지 않도록 비활성화를 안내합니다.

### REQ-03-02. 채널과 프로젝트 연결

모든 영상 프로젝트는 제작팀에 등록된 하나의 담당 Channel을 지정합니다. 이 값은 제작 단계의 분류, 검색과 영상 결과물의 초기값이며 실제 게시 Channel을 확정하는 값은 아닙니다.

실제 업로드 Channel은 YouTube 게시물마다 별도로 저장합니다. 영상 결과물을 처음 게시할 때는 대표 프로젝트의 담당 Channel을 기본값으로 제안하되 사용자가 같은 제작팀의 다른 활성 Channel을 선택할 수 있어야 합니다.

프로젝트 그룹은 채널을 직접 소유하지 않습니다. 하나의 프로젝트 그룹에 속한 여러 프로젝트는 서로 다른 채널에 연결될 수 있습니다.

### REQ-03-03. YouTube 채널 연동

사용자는 필요한 경우 Google OAuth를 통해 자신이 권한을 가진 YouTube 채널을 YMS와 연결할 수 있습니다.

연동이 해제되더라도 기존 프로젝트와 YMS 내부 데이터는 유지되어야 하며, 외부 API를 통해 새 데이터를 갱신하는 기능만 제한합니다.

## 5. 프로젝트 그룹 관리

### REQ-04-01. 선택적 프로젝트 그룹 생성

OWNER와 ADMIN은 관련된 여러 영상 프로젝트의 비용과 외부 수익을 하나의 분석 단위로 관리하기 위해 제작팀에 프로젝트 그룹을 생성할 수 있습니다.

프로젝트 그룹은 소규모 제작팀의 기본 협업 흐름에 필수인 단계가 아닙니다. 프로젝트 그룹을 만들지 않아도 프로젝트 생성, 협업과 개별 성과 분석 기능을 모두 사용할 수 있어야 합니다.

프로젝트 그룹에는 다음 정보를 관리합니다.

- 프로젝트 그룹명: 필수, 1자 이상 150자 이하
- 설명: 선택
- 시작일: 선택
- 종료일: 선택
- 상태: 필수, 최초 생성 시 PLANNING

같은 제작팀에서는 이름의 앞뒤 공백을 제거하고 영문 대소문자를 구분하지 않았을 때 같은 프로젝트 그룹명을 중복해서 사용할 수 없습니다. 완료 또는 취소된 프로젝트 그룹의 이름도 중복 검사에 포함합니다.

프로젝트 그룹은 제작팀에 직접 속하며 특정 채널에 귀속되지 않습니다.

### REQ-04-02. 프로젝트 그룹과 프로젝트 연결

프로젝트 그룹과 프로젝트의 관계는 **ProjectGroup 1 : N Project**로 정의합니다.

하나의 프로젝트 그룹에는 여러 영상 프로젝트를 연결할 수 있으며, 하나의 프로젝트는 최대 하나의 프로젝트 그룹에만 속할 수 있습니다.

영상 프로젝트는 프로젝트 그룹을 선택하지 않고 독립적으로 생성할 수도 있어야 합니다.

예를 들어 하나의 브랜드 계약에 롱폼 영상 2편과 쇼츠 3편이 포함되어 있다면 각 콘텐츠는 별도의 영상 프로젝트로 관리하고 동일한 프로젝트 그룹에 연결할 수 있습니다.

OWNER와 ADMIN만 프로젝트와 프로젝트 그룹의 연결을 생성, 변경하거나 해제할 수 있습니다. 프로젝트 편집 권한만으로 프로젝트 그룹 연결 권한을 부여하지 않습니다.

프로젝트 그룹 생성 과정의 선택 연결, 기존 그룹에 대한 추가 연결, 다른 그룹으로의 이동과 연결 해제 모두 같은 콘텐츠 성과 이동 확인 정책을 적용합니다. 해당 프로젝트가 대표인 VideoContent의 동기화된 성과 또는 계산 가능한 예상 플랫폼 수익이 있으면 집계 대상도 바뀐다는 점을 확인하고, 영향 데이터가 없으면 불필요한 확인 없이 저장합니다. 다른 그룹으로 이동하거나 연결을 해제할 때 작업자 지급 금액이나 프로젝트 직접 비용·수익도 있으면 실제 재무와 참고용 콘텐츠 성과의 이동 여부를 구분하여 안내합니다. 프로젝트에 직접 귀속된 비용과 수익은 프로젝트를 따라 새 그룹의 집계에 반영하고, 기존 프로젝트 그룹에 직접 귀속된 비용과 수익은 원래 그룹에 유지합니다.

여러 프로젝트를 한 번에 연결할 때는 모든 대상의 소속과 영향 확인을 먼저 검증하고 전체를 한 번에 반영합니다. 검증이나 확인이 실패하면 프로젝트 그룹 생성과 어떤 프로젝트 연결도 부분 적용하지 않습니다.

완료 또는 취소된 프로젝트 그룹에는 새 프로젝트를 연결할 수 없습니다. 다시 연결해야 한다면 먼저 상태를 ACTIVE로 변경합니다.

### REQ-04-03. 프로젝트 그룹 단위 비용과 수익 집계

프로젝트 그룹 단위에서는 다음 금액을 합산하여 조회할 수 있어야 합니다.

- 프로젝트 그룹에 직접 귀속된 비용
- 프로젝트 그룹에 직접 귀속된 실제 수익
- 프로젝트 그룹에 속한 각 프로젝트에 직접 귀속된 비용
- 프로젝트 그룹에 속한 각 프로젝트에 직접 귀속된 실제 수익

채널 또는 제작팀에 귀속된 비용과 수익을 프로젝트 그룹에 임의로 배분하여 포함하지 않습니다.

OWNER와 ADMIN은 프로젝트 그룹 상세 화면에서 협찬, 제휴, 상품 판매 등 실제로 발생했거나 금액이 확정된 외부 수익을 수동으로 등록할 수 있어야 합니다. 계약 예정액, 청구, 입금 여부, 미수금과 세금계산서 관리는 초기 범위에 포함하지 않습니다.

프로젝트 그룹 상세에서 등록하는 비용과 수익은 귀속 대상을 현재 프로젝트 그룹으로 고정하고, 공통 Expense / Revenue 관리 기능을 재사용합니다. 조회수 기반 예상 YouTube 수익은 실제 수익에 포함하지 않습니다.

### REQ-04-04. 프로젝트 그룹 상태 관리

프로젝트 그룹은 최소한 다음 상태를 구분하여 관리합니다.

- PLANNING: 준비 중
- ACTIVE: 진행 중
- COMPLETED: 완료
- CANCELLED: 취소

완료 또는 취소된 프로젝트 그룹의 프로젝트, 비용과 수익 이력은 보존해야 합니다.

COMPLETED와 CANCELLED 상태에서는 새 프로젝트 연결을 제한하지만, 뒤늦게 확정된 수익이나 이미 발생한 비용을 등록하고 정정할 수 있습니다. OWNER와 ADMIN은 필요한 경우 해당 상태를 ACTIVE로 되돌릴 수 있습니다.

### REQ-04-05. 프로젝트 그룹 삭제

연결된 프로젝트가 없고 직접 귀속된 Expense와 Revenue도 없는 프로젝트 그룹만 물리 삭제할 수 있습니다.

삭제 요청 시 서버가 연결 데이터를 최종 확인합니다. 프로젝트, 비용 또는 수익이 하나라도 존재하면 삭제를 거부하고 COMPLETED 또는 CANCELLED 상태로 이력을 보존하도록 안내합니다.

### REQ-04-06. 프로젝트 그룹 권한과 정보 노출

프로젝트 그룹 목록, 상세, 연결 프로젝트 전체와 재무 정보는 OWNER와 ADMIN에게만 제공합니다.

MEMBER는 자신이 참여한 프로젝트에서 소속 프로젝트 그룹의 이름만 확인할 수 있습니다. 프로젝트 그룹 이름은 관리 화면 링크로 제공하지 않으며, 다른 연결 프로젝트, 설명, 비용, 수익과 재무 성과는 노출하지 않습니다.

## 6. 프로젝트와 작업 관리

### REQ-05-01. 영상 프로젝트 생성

현재 제작팀의 모든 ACTIVE 멤버는 다음 정보를 입력하여 영상 프로젝트를 생성할 수 있습니다.

- 프로젝트 제목: 필수, 앞뒤 공백 제거 후 1자 이상 150자 이하
- 기획 내용: 선택, 최대 2,000자
- 담당 채널: 필수, 현재 제작팀의 활성 Channel
- 프로젝트 그룹(선택)
- 영상 유형: 필수, LONG / SHORTS 중 명시적으로 선택
- 프로젝트 상태: 필수, 생성 시 PLANNING / EDITING 중 선택하고 기본값은 PLANNING
- 제작 마감일: 선택
- 업로드 예정일: 선택

프로젝트를 생성한 사용자는 해당 프로젝트의 소유자가 되고 EDIT 참여자로 자동 등록됩니다. OWNER와 ADMIN만 생성 시 프로젝트 그룹을 지정할 수 있으며 MEMBER가 생성한 프로젝트의 그룹은 미지정으로 저장합니다. 수동 등록 Channel도 사용할 수 있지만 비활성 Channel과 완료·취소된 ProjectGroup은 새 프로젝트에 지정할 수 없습니다.

프로젝트 제목은 같은 제작팀 안에서 중복을 허용합니다. 두 일정은 모두 생략하거나 하나만 입력할 수 있고, 둘 다 입력하면 제작 마감일이 업로드 예정일보다 늦을 수 없습니다. 기존 프로젝트의 사후 등록을 위해 과거 날짜도 허용합니다.

### REQ-05-01-1. 프로젝트와 영상 결과물의 분리

Project는 일정, 참여자, Task, 비용과 협업을 관리하는 제작 과정이며, VideoContent는 시청자에게 한 편으로 인식되는 완성 영상 결과물입니다. Project 자체를 YouTube Video ID와 직접 연결하지 않습니다.

하나의 Project에서 롱폼과 쇼츠 또는 여러 편의 영상 결과물이 만들어질 수 있고, 여러 Project의 작업 결과를 하나의 영상 결과물로 합칠 수도 있으므로 Project와 VideoContent는 다대다 관계로 관리합니다. 아직 결과물이 없는 Project와 아직 게시되지 않은 VideoContent도 정상 상태로 허용합니다.

VideoContent에는 집계 기준이 되는 대표 Project를 하나 지정하고 대표 Project도 연결 Project 중 하나여야 합니다. 연결된 모든 Project 상세에서 영상 결과물과 공개 성과를 조회할 수 있지만 Project 및 ProjectGroup별 콘텐츠 성과와 예상 플랫폼 수익 집계에는 대표 Project만 사용하여 중복 집계를 방지합니다.

Project의 영상 유형은 이후 생성하는 VideoContent의 초기값입니다. 실제 LONG / SHORTS 유형은 VideoContent마다 선택하며, 여러 Project를 합치는 경우 대표 Project의 값을 기본으로 제안하되 사용자가 변경할 수 있어야 합니다.

대표 Project를 같은 ProjectGroup 안에서 변경하거나 양쪽 모두 ProjectGroup이 없으면 현재·새 Project를 모두 관리할 수 있는 프로젝트 소유자, EDIT 참여자와 Workspace OWNER·ADMIN이 변경할 수 있습니다. 서로 다른 ProjectGroup 사이 또는 그룹 있음·없음 사이의 변경은 Workspace OWNER·ADMIN만 수행합니다. 대표 Project 변경 이력에는 이전·새 Project, 변경 당시 양쪽 ProjectGroup, 사유, 변경자와 시각을 보존합니다.

대표 Project 변경으로 ProjectGroup별 콘텐츠 성과가 실제로 이동하고 동기화된 성과 또는 계산 가능한 예상 플랫폼 수익이 존재할 때는 저장 전에 영향을 확인합니다. 같은 원칙은 대표 Project 자체의 ProjectGroup을 변경하는 경우에도 적용하며, 실제 Expense·Revenue·손익·ROI와 참고용 콘텐츠 성과의 이동 여부를 구분하여 안내합니다.

### REQ-05-02. 프로젝트 일정 구분

영상 프로젝트에서는 다음 일정을 서로 구분하여 관리합니다.

- 제작 마감일(due date): 편집, 썸네일 등 제작 작업을 완료해야 하는 기준일
- 업로드 예정일(planned upload date): 영상을 공개할 계획인 날짜
- 실제 게시 일시(published at): YouTube 게시물이 실제로 업로드 또는 공개된 일시

실제 게시 일시는 Project가 아니라 YouTubePublication마다 직접 입력하거나 YouTube 연동을 통해 가져옵니다. Project를 UPLOADED로 변경해도 현재 시각이나 게시물을 자동 생성하지 않으며, 게시물 생성도 Project 상태를 자동 변경하지 않습니다. YouTube에서 확인한 게시 일시와 기존 수동 입력값이 다르면 덮어쓰지 않고 차이를 안내합니다.

### REQ-05-03. 프로젝트 참여자와 권한

프로젝트 소유자 또는 Workspace OWNER와 ADMIN은 현재 제작팀 멤버를 프로젝트 참여자로 추가하고 권한을 변경하거나 제거할 수 있습니다. 프로젝트 밖 사용자를 초대하는 기능과 구분하기 위해 화면에서는 `참여자 추가`로 표시합니다.

참여자 추가는 Workspace의 ACTIVE 멤버를 복수 선택하고 EDIT 또는 VIEW 중 하나의 공통 권한을 지정하는 방식으로 제공합니다. 요청 대상 중 다른 Workspace의 멤버, 비활성 멤버 또는 이미 활성 참여 중인 멤버가 하나라도 있으면 전체 요청을 취소하고 후보 목록을 새로 조회합니다. 현재 참여 종료 상태이며 Workspace에서는 ACTIVE인 멤버를 다시 추가할 때는 기존 Project Member를 재활성화하고 새 권한과 참여 시각을 기록하며, 이전 권한을 자동 복구하지 않습니다. Workspace에서 LEFT 또는 REMOVED인 멤버에게는 Project의 `다시 참여` 동작을 제공하지 않고 각각 탈퇴·제외 상태와 제작팀 재초대가 먼저 필요함을 안내합니다.

참여자에게는 다음 프로젝트 권한을 부여합니다.

- EDIT: 프로젝트 조회 및 기본 정보·상태·작업 수정과 협업 기능 사용 가능. 참여자 권한, 프로젝트 그룹, 수익 설정, 보관과 삭제는 변경 불가
- VIEW: 프로젝트 및 관련 정보를 조회할 수 있으나 변경할 수 없음

프로젝트 소유자는 자신을 참여자 목록에서 제거하거나 VIEW로 낮출 수 없습니다. 프로젝트 참여자가 아닌 일반 MEMBER의 접근은 차단하지만 Workspace OWNER와 ADMIN은 참여자로 자동 등록되지 않아도 같은 제작팀의 모든 프로젝트를 조회하고 관리할 수 있습니다. 관리 접근만으로 프로젝트 채팅 읽음 상태를 만들지 않습니다.

EDIT 참여자를 VIEW로 변경하거나 프로젝트에서 제외해도 기존 Task의 담당자 참조와 완료 이력은 유지합니다. 미완료 Task에는 각각 `권한 부족 · 담당자 재지정 필요` 또는 `참여 종료 · 담당자 재지정 필요` 상태를 표시하고, 새 Task 담당자는 ACTIVE EDIT 참여자 중에서만 선택합니다.

같은 Project Member가 ACTIVE EDIT로 재참여하면 여전히 해당 Project Member를 담당자로 참조하는 미완료 Task의 담당 자격과 수정 권한을 자동 회복하고 재지정 필요 표시를 제거합니다. 재참여 전에 다른 담당자로 변경된 Task와 완료 Task에는 영향을 주지 않습니다. VIEW 재참여는 기존 담당 자격을 회복하지 않습니다.

프로젝트 소유자와 Workspace OWNER·ADMIN은 논리 삭제되지 않은 프로젝트의 소유권을 같은 프로젝트의 다른 ACTIVE EDIT 참여자에게 이전할 수 있습니다. VIEW 참여자나 프로젝트 미참여자는 먼저 별도의 권한 변경 또는 참여자 추가를 완료해야 합니다. 이전 소유자는 ACTIVE 멤버인 동안 일반 EDIT 참여자로 남습니다. 소유권 이전 화면은 대상 이름과 복사 가능한 이메일 및 영향을 제시하고, 사용자가 대상 이메일을 정확히 입력해야 최종 실행할 수 있습니다. Workspace OWNER·ADMIN에게는 이전 후에도 제작팀 관리 권한으로 다시 변경할 수 있음을, 일반 Project Owner에게는 다시 변경하려면 새 소유자 또는 제작팀 관리자의 협조가 필요함을 구분해 안내합니다.

보관된 프로젝트에서는 참여자와 현재 참여 종료자를 조회할 수 있지만 참여자 추가, 재참여, 권한 변경과 제외는 수행할 수 없습니다. Workspace 멤버 생명주기와의 교착을 피하기 위해 기존 ACTIVE EDIT 참여자를 대상으로 한 소유권 이전만 예외적으로 허용하며 이전 후에도 보관 상태를 유지합니다. 대상이 없다면 프로젝트를 복원하여 EDIT 참여자를 확보해야 합니다.

Project Member의 최초 참여, 재참여, EDIT·VIEW 권한 변경과 참여 종료는 변경 전후 값, 처리자, 처리 시각과 발생 경로를 별도 감사 이력으로 보존합니다. Project 소유권 이전도 이전·신규 소유자, 처리자와 시각을 별도 이력으로 보존합니다. Project Owner와 Workspace OWNER·ADMIN만 이력을 조회할 수 있습니다.

기존 Project Member에는 현재 참여 정보를 기준으로 SYSTEM이 생성한 초기 이력을 추가합니다. 기존 `joined_at`, 현재 권한과 참여 상태만 사용하고 알 수 없는 과거 권한 변경이나 재참여 사건은 추정하지 않습니다.

Mock에서는 Project Member 추가·재참여·권한 변경·제외·소유권 이전과 Workspace 멤버 제외·탈퇴를 Workspace 단위로 직렬화합니다. 실제 데이터베이스에서는 관련 Workspace Member, Project, Project Member를 순서대로 잠근 뒤 최신 상태를 다시 검증하고 저장 직전에 현재 Project Owner가 ACTIVE EDIT Project Member인지 확인합니다.

### REQ-05-04. 프로젝트 상태 관리

프로젝트는 기본적으로 다음 진행 상태를 가집니다.

- PLANNING: 기획 단계
- EDITING: 제작 진행 중
- REVIEW: 검수 중
- UPLOADED: 업로드 완료
- CANCELLED: 제작 취소

프로젝트 상태는 엄격한 결재 절차가 아니라 업무 진행을 나타내는 표지로 사용합니다. 생성 이후 프로젝트 소유자, EDIT 참여자와 Workspace OWNER·ADMIN은 모든 상태 사이를 직접 변경할 수 있고 이전 단계로 되돌리거나 CANCELLED 프로젝트를 재개할 수 있습니다. 변경 전후 상태, 변경자와 변경 시각을 이력으로 기록합니다.

UPLOADED 상태 변경은 영상 결과물 또는 YouTube 게시물 생성과 외부 동기화를 자동 실행하지 않습니다. 보관된 프로젝트를 PLANNING, EDITING 또는 REVIEW로 변경하면 보관을 자동 해제합니다.

### REQ-05-05. 프로젝트 취소

더 이상 제작하지 않는 프로젝트는 삭제하지 않고 CANCELLED 상태로 변경할 수 있습니다.

취소된 프로젝트는 기본 진행 목록에서 제외하되 이력, 작업 비용, 채팅 등 기존 데이터는 유지합니다.

이미 발생한 제작 비용이 있는 경우 취소 프로젝트도 정산 대상에 포함할 수 있어야 합니다.

### REQ-05-06. 프로젝트 보관

UPLOADED 또는 CANCELLED 프로젝트만 보관(archive)할 수 있습니다. 프로젝트 소유자와 Workspace OWNER·ADMIN이 보관하거나 보관을 해제할 수 있습니다.

보관된 프로젝트는 기본 프로젝트 목록과 일정 화면에서 제외하지만 별도의 보관 목록에서 조회할 수 있어야 합니다.

보관 상태는 해제할 수 있어야 하며 프로젝트의 업무 상태와는 별도로 관리합니다.

### REQ-05-07. 프로젝트 삭제

프로젝트 소유자 또는 Workspace OWNER·ADMIN만 프로젝트 삭제를 요청할 수 있습니다.

삭제 전 사용자에게 확인 절차를 제공하고 항상 논리 삭제하여 삭제자와 삭제 시각을 기록합니다. 삭제된 프로젝트는 프로젝트 목록, 보관함, 검색, 일정과 콘텐츠 성과 분석에서 제외하고 조회수 기반 예상 수익도 집계하지 않습니다.

하위 작업, 채팅, 실제 Expense, 실제 Revenue와 Settlement 이력은 보존합니다. 이미 발생하거나 확정된 실제 금액은 재무 합계에서 제외하지 않고 `삭제된 프로젝트 · {기존 프로젝트명}`으로 출처를 유지하되 삭제된 프로젝트 상세 링크는 제공하지 않습니다. 프로젝트 삭제만으로 미확정 작업자 지급 예정액을 취소하지 않습니다.

삭제 대상 Project가 VideoContent의 대표이고 다른 활성 연결 Project가 있으면 삭제 과정에서 VideoContent별 새 대표를 사용자가 직접 선택해야 합니다. 후보가 하나뿐이면 미리 선택하되 확인을 생략하지 않으며 대표 변경과 Project 논리 삭제를 하나의 업무 처리로 수행합니다.

다른 활성 연결 Project가 없으면 삭제를 허용하고 삭제된 Project를 역사적 대표로 계속 참조합니다. VideoContent, YouTubePublication과 연결 이력은 보존하지만 활성 Project 및 ProjectGroup 콘텐츠 성과 집계에서는 제외합니다. 이후 활성 Project를 연결하여 새 대표로 지정하면 집계에 다시 포함합니다. Project 삭제는 연결을 제거하지 않으므로 마지막 Project 연결 해제를 차단하는 규칙과 충돌하지 않습니다.

### REQ-05-08. 세부 작업 등록

하나의 영상 프로젝트에는 여러 세부 작업을 등록할 수 있습니다.

각 작업에는 다음 정보를 관리합니다.

- 작업 종류
- 작업 내용: 선택 입력이며 미입력 시 작업 종류명을 화면 제목으로 사용
- 담당자
- 시작일
- 종료일
- 작업자 지급 예정 금액
- 작업 상태

작업의 사용자 표시명은 `작업`, 분류의 표시명은 `작업 종류`로 통일합니다. 작업 내용은 한 줄 150자 이하로 입력하며 별도의 작업 설명 필드는 두지 않습니다.

작업 종류, 담당자와 작업자 지급 예정 금액은 필수이고 시작일과 종료일은 각각 선택값입니다. 담당자는 전문 역할과 관계없이 지정할 수 있지만 현재 Project의 ACTIVE EDIT 참여자여야 합니다. 전문 역할은 프로필 정보와 담당자 검색·필터에만 사용하며 작업 적합성을 판정하거나 배정을 제한하지 않습니다.

Project Owner, ACTIVE EDIT 참여자와 Workspace OWNER·ADMIN은 작업 생성·수정·논리 삭제·복원 권한을 동일하게 가집니다. VIEW 참여자는 작업을 조회할 수 있지만 변경할 수 없습니다. 보관된 Project에서는 작업을 조회만 할 수 있으며 Project의 업무 상태 자체는 작업 변경을 제한하지 않습니다.

### REQ-05-09. 확장 가능한 작업 종류

시스템은 기본 작업 종류를 제공하되 특정 종류만 코드에 고정하지 않는 확장 가능한 구조로 설계합니다.

기본 작업 종류의 예시는 다음과 같습니다.

- 가편집
- 종합 편집
- 자막
- 썸네일

향후 촬영, 모션그래픽, 번역, 더빙, 쇼츠 재가공 등 새로운 작업 종류를 추가할 수 있어야 합니다.

제작팀에서 기본 및 사용자 정의 작업 종류를 추가, 수정, 비활성화, 재활성화하거나 삭제할 수 있도록 확장 가능하게 설계합니다.

기존 프로젝트에서 사용된 작업 종류를 비활성화하더라도 과거 작업 이력은 유지되어야 합니다.

작업 종류의 비활성화와 삭제는 별개의 기능으로 제공합니다. 삭제 요청 시 서버가 기존 작업의 사용 여부를 최종 확인하며, 사용 이력이 없는 작업 종류만 물리 삭제합니다. 논리 삭제된 작업도 복원 가능한 사용 이력으로 간주하므로 참조 중인 작업 종류의 물리 삭제를 차단합니다. 기존 작업에서 사용 중이면 삭제를 거부하고 더 이상 새 작업에서 선택하지 않도록 비활성화를 안내합니다.

### REQ-05-10. 작업 상태 관리

작업자는 자신에게 배정된 작업의 진행 상태를 다음 순서로 변경할 수 있습니다.

대기 → 진행 중 → 검수 요청 → 완료

시스템 내부 상태는 다음 값을 기본으로 사용합니다.

- WAITING
- PROGRESS
- REVIEW
- COMPLETED

신규 작업은 항상 WAITING 상태로 생성합니다. 담당자인 ACTIVE EDIT 참여자는 자신의 작업 상태를 순서대로 변경할 수 있고 Project Owner, ACTIVE EDIT 참여자와 Workspace OWNER·ADMIN은 Project의 모든 작업 상태를 같은 전이 규칙 안에서 조정할 수 있습니다. 상태 건너뛰기는 허용하지 않습니다.

검수 반려는 REVIEW → PROGRESS로 처리하고 500자 이하 반려 사유를 필수로 기록합니다. 확정 정산에 포함되지 않은 완료 작업은 확인 후 COMPLETED → REVIEW로 완료를 취소할 수 있으며, 일반 정보를 수정하려면 다시 REVIEW → PROGRESS 반려 절차를 거칩니다. WAITING과 PROGRESS에서만 일반 정보를 수정할 수 있습니다.

담당자 본인이 Project Owner 또는 상태 조정 권한자라면 자신의 작업도 완료할 수 있습니다. 검수 단계는 별도 검수자 직무를 강제하는 절차가 아니라 작업 흐름의 확인 지점으로 사용합니다.

논리 삭제되지 않은 작업이 하나 이상 있고 마지막 미완료 작업이 완료되면, 권한 있는 사용자에게 영상 업로드까지 마친 경우 Project를 UPLOADED 상태로 전환할 수 있다고 선택적으로 안내합니다. 사용자가 선택하지 않아도 작업 완료는 유지하며 이후 작업 추가·복원·완료 취소가 Project 상태를 자동으로 되돌리지는 않습니다.

### REQ-05-10-1. 작업 삭제와 복원

작업은 상태와 관계없이 논리 삭제하고 삭제자와 삭제 시각을 기록합니다. 삭제된 작업은 기본 목록, 작업 수, 작업자 지급 예정 금액, ProjectGroup 비용, 일정, 미완료 작업 수, 검수 요청 수와 알림 대상에서 제외합니다. 삭제된 작업은 별도 접이식 목록에서 조회하고 기존 상태·담당자·일정·금액을 유지한 채 복원할 수 있습니다.

복원 시 작업 종류가 비활성 상태여도 기존 값을 유지합니다. 담당자가 더 이상 ACTIVE EDIT 참여자가 아니면 복원을 허용하되 `담당자 재지정 필요` 상태를 표시하고 상태 변경을 차단합니다. 보관된 Project에서는 Project를 복원하기 전까지 작업 삭제와 복원을 수행할 수 없습니다.

CONFIRMED Settlement Item에 포함된 작업은 정보 수정, 상태 변경, 완료 취소와 논리 삭제를 모두 차단합니다. 먼저 정산 취소 또는 정정 절차를 거쳐야 합니다. 영구 삭제 기능은 제공하지 않습니다.

삭제와 복원 전에는 작업, 담당자, 상태, 지급 예정 금액과 집계 영향을 안내하는 확인 단계를 제공합니다. 삭제된 작업은 모든 Project 조회 권한자가 볼 수 있고 VIEW에는 복원 액션을 제공하지 않으며, 기존 금액 공개 범위를 동일하게 적용합니다.

### REQ-05-10-2. 작업 변경 이력과 동시성

작업 생성, 일반 정보 수정, 상태 변경, 검수 반려, 논리 삭제와 복원을 통합 이력으로 기록합니다. 처리자와 처리 시각을 공통 기록하고, 수정은 실제 변경된 필드의 이전 값과 변경 값을, 상태 변경은 이전·이후 상태를, 반려는 사유를 보존합니다. 같은 값을 다시 저장하면 이력을 만들지 않습니다.

Task에는 version을 두고 수정·상태 변경·삭제·복원 요청 시 조회 당시 version을 검증합니다. 최신 값과 다르면 충돌로 거부하고 화면은 최신 작업을 다시 조회합니다.

### REQ-05-11. 캘린더 기반 일정 조회

프로젝트와 작업 일정은 메인 대시보드 또는 스케줄러 화면에서 달력 형태로 확인할 수 있어야 합니다.

시작일과 종료일이 모두 있는 작업은 달력 위에서 기간 일정으로 표시합니다. 시작일만 있으면 시작일 하루 일정, 종료일만 있으면 종료일 하루 마감 일정으로 표시하고 두 날짜가 모두 없으면 작업 목록과 요약에만 표시합니다.

사용자는 일정이 겹치는 작업과 특정 작업자에게 집중된 업무를 쉽게 파악할 수 있어야 합니다.

일정과 오늘 마감 작업을 선택하면 `/projects/{projectId}/tasks?taskId={taskId}`로 이동하여 대상 작업을 강조합니다. 대상 작업이 삭제됐거나 현재 권한으로 조회할 수 없으면 Project 작업 화면은 유지하고 요청한 작업을 확인할 수 없다고 안내합니다.

작업 생성·수정·삭제·복원과 상태 변경은 Project 작업 수, 완료 수, 작업자 지급 예정 금액, Project Member의 미완료 담당 작업 수, 대시보드 일정과 검수 요청 요약에 즉시 반영합니다. Task 저장소를 이 집계들의 단일 기준으로 사용합니다.

### REQ-05-12. 일정 필터와 검색

스케줄러에서는 다음 조건을 조합하여 일정을 조회할 수 있어야 합니다.

- 조회 기간
- 프로젝트 상태
- 담당 전문 역할
- 내가 담당한 작업
- 채널
- 프로젝트 또는 작업 관련 키워드

## 7. 프로젝트 채팅과 알림

### REQ-06-01. 프로젝트별 채팅방

영상 프로젝트가 생성되면 해당 프로젝트 전용 채팅 공간을 사용할 수 있어야 합니다.

프로젝트 소유자와 참여자만 채팅방에 접근할 수 있으며 권한이 없는 사용자의 접근은 차단합니다.

### REQ-06-02. 실시간 메시지 송수신

프로젝트 채팅 메시지는 화면을 새로고침하지 않아도 실시간으로 전송되고 표시되어야 합니다.

실시간 통신은 WebSocket 기반으로 구현하는 것을 기본 방향으로 합니다.

### REQ-06-03. 대화 이력 보존

모든 채팅 메시지는 데이터베이스에 저장합니다.

사용자가 채팅방에 다시 입장하면 최근 메시지를 우선 조회하고 이전 메시지는 추가로 불러올 수 있어야 합니다.

메시지가 많아지는 경우를 고려하여 페이지 또는 커서 단위 조회가 가능해야 합니다.

### REQ-06-04. 읽지 않은 메시지

사용자별로 프로젝트 채팅의 마지막 확인 위치를 관리합니다.

사용자는 프로젝트별 읽지 않은 메시지 수를 확인할 수 있어야 하며 채팅방을 확인하면 읽음 상태가 갱신되어야 합니다.

### REQ-06-05. 알림 제공

사용자에게 자신과 관련된 주요 변경 사항을 알림으로 제공합니다.

초기 알림 대상에는 최소한 다음 이벤트를 포함합니다.

- 자신에게 배정된 작업의 변경
- 작업 상태 변경 및 검수 요청
- 참여 중인 프로젝트의 새 채팅 메시지
- 제작팀 초대
- 자신의 정산 상태 변경

향후 다른 이벤트를 추가할 수 있도록 알림 유형을 확장 가능한 구조로 설계합니다.

### REQ-06-06. 알림 조회 및 읽음 처리

사용자는 전체 알림과 읽지 않은 알림을 조회할 수 있어야 합니다.

시스템은 읽지 않은 알림 수를 제공하고 사용자가 알림을 확인하면 읽음 상태를 기록합니다.

알림 목록은 최근 항목부터 조회하며 조회 개수를 제한할 수 있어야 합니다.

## 8. 대시보드와 업무 현황

### REQ-07-01. 대시보드 요약 카드

사용자는 현재 업무 상태를 빠르게 확인할 수 있도록 자신의 권한과 역할에 맞는 요약 정보를 카드 형태로 확인할 수 있어야 합니다.

기본 업무 요약에는 다음 정보를 포함합니다.

- 진행 중 프로젝트 수
- 내가 담당한 마감 예정 작업 수
- 검수 요청 중인 작업 수
- 마감 임박 작업 수

각 요약 카드는 관련 프로젝트 또는 작업 목록으로 이동할 수 있도록 확장합니다.

대시보드 상단에는 현재 제작팀 이름과 `새 프로젝트` 동작을 제공합니다. `새 프로젝트`는 `/projects?create=true`로 이동하여 SCR-07 생성 모달을 열고, 모달이 열려 있는 동안 Query를 유지하여 새로고침과 직접 링크에서도 같은 상태를 복원합니다. 모달을 닫거나 생성에 성공하면 생성 Query를 제거합니다.

### REQ-07-02. 프로젝트 진척률

진행 중인 전체 프로젝트의 상태 비율을 차트로 표시합니다.

각 프로젝트에서는 완료된 세부 작업과 전체 세부 작업의 비율을 이용하여 진척률을 계산하고 진행 바로 표시합니다.

### REQ-07-03. 작업자별 업무량

권한이 있는 사용자는 작업자별로 배정된 작업 수와 진행 중인 작업 수를 비교할 수 있어야 합니다.

특정 작업자에게 업무가 집중되었는지 확인할 수 있도록 시각화하고 새로운 작업을 배정할 때 참고할 수 있도록 합니다.

### REQ-07-04. 역할별 대시보드 구성

OWNER와 ADMIN에게는 제작팀 운영 현황과 재무 분석으로 이동할 수 있는 정보를 제공합니다.

EDITOR, THUMBNAILER 등 일반 작업자에게는 자신의 작업, 마감, 검수 요청, 채팅과 정산 현황을 우선적으로 제공합니다.

재무 정보에 접근 권한이 없는 사용자에게는 전체 매출, 총비용, 이익 또는 ROI를 기본 대시보드에 노출하지 않습니다.

OWNER와 ADMIN은 현재 제작팀의 비삭제·비보관 업무 범위를 조회하고, MEMBER는 자신이 참여한 Project와 접근 가능한 Task만 조회합니다. `MY_TASK` 필터는 이 권한 범위를 넓히지 않고 현재 사용자에게 배정된 Task로 다시 제한합니다. 권한 필터는 화면 숨김이 아니라 Dashboard API 응답 경계에서 적용합니다.

데스크톱에서는 월간 Calendar를 기본으로 사용하고 Calendar 오른쪽에 오늘 마감과 최근 알림을 세로로 배치합니다. 모바일에서는 같은 기능과 조작 순서를 유지하면서 주간 목록형 Agenda를 초기 View로 사용하고, 요약 카드는 2열 이하로 줄입니다. 사용자가 Calendar View를 직접 바꾼 뒤에는 화면 크기 변경만으로 선택을 강제로 되돌리지 않습니다.

### REQ-07-05. 제작팀 기반 공통 내비게이션

현재 제작팀을 사용하는 주요 인증 화면은 공통 헤더와 내비게이션 안에서 이동할 수 있어야 합니다.

공통 헤더에는 현재 제작팀 표시와 전환, 주요 업무 메뉴, 읽지 않은 알림 수, 알림 Drawer 진입점과 사용자 메뉴를 제공합니다. 사용자 메뉴를 열면 현재 로그인 계정을 바로 확인하고 이메일을 복사할 수 있도록 이름과 이메일을 메뉴 동작보다 먼저 표시합니다.

상위 메뉴는 다음 순서를 유지합니다.

1. 대시보드
2. 프로젝트
3. 메신저
4. 정산
5. 분석
6. 비용·수익
7. 제작팀 관리

프로젝트 메뉴 안에는 `/projects` 프로젝트 탭과 `/project-groups` 프로젝트 그룹 탭을 같은 위치에 제공합니다. 두 탭은 같은 상위 메뉴를 공유하지만 Route, 화면, 조회와 관리 로직이 분리된 별개 기능입니다. 프로젝트 그룹 탭은 OWNER와 ADMIN에게만 표시하며 MEMBER에게는 프로젝트 탭만 제공합니다. 권한상 표시할 탭이 하나뿐이면 전환 기능이 없으므로 탭 영역 자체를 표시하지 않습니다.

프로젝트 그룹을 사용하지 않는 제작팀에도 OWNER와 ADMIN에게 탭은 표시하되 생성이나 사용을 강제하지 않습니다. 별도의 기능 활성화 설정은 두지 않습니다.

분석부터 제작팀 관리까지의 관리 영역은 OWNER와 ADMIN에게만 제공합니다. MEMBER에게는 제작팀 전체 재무 정보 또는 관리 기능으로 이동하는 메뉴를 노출하지 않습니다.

정산 메뉴는 내비게이션에서 같은 위치를 사용하지만 역할에 따라 별개의 기능으로 제공합니다. OWNER와 ADMIN에게는 `정산 관리` 메뉴와 `/workspace/settlements` 경로를, MEMBER에게는 `내 정산` 메뉴와 `/my/settlements` 경로를 제공합니다. 두 기능은 화면, Route와 조회 로직을 분리하고 자동으로 서로 전환하지 않습니다.

아직 업무 화면이 구현되지 않은 메뉴도 확정된 Route를 먼저 제공하고 공통 준비 중 화면을 표시합니다. 준비 중 화면은 공통 헤더를 유지하고 대시보드로 이동할 수 있어야 합니다.

### REQ-07-06. 제작팀 전환과 화면 연속성

제작팀을 전환해도 새 제작팀에서 같은 기능을 이용할 수 있다면 현재 기능을 유지하여 반복 이동을 줄여야 합니다.

- 목록 화면은 같은 기능의 목록 Route를 유지합니다.
- 상세 화면은 이전 제작팀의 리소스 ID와 선택 상태를 제거하고 새 제작팀의 같은 기능 목록으로 이동합니다.
- 새 제작팀에도 적용 가능한 검색과 필터 상태는 가능한 범위에서 유지합니다.
- 전환 완료 시 `{제작팀명} 제작팀으로 전환했습니다.`라는 정보성 안내만 표시합니다.
- 새 제작팀에서 현재 기능을 사용할 수 없다면 다른 기능으로 자동 이동하지 않고 접근 불가 화면을 표시합니다.

사용자가 직접 URL, 알림 또는 저장된 링크로 접근할 때 권한이 없거나, 화면을 사용하는 동안 권한 변경으로 API가 403을 반환한 경우에도 접근 불가 화면을 제공합니다. 접근 불가 화면에는 현재 제작팀 이름을 표시하고 제작팀 전환과 대시보드 이동 수단을 제공합니다.

다른 제작팀에 속한 리소스를 현재 제작팀에서 열었거나 리소스 존재 여부를 공개할 수 없는 경우에는 권한 부족과 리소스 부재를 구체적으로 구분하지 않습니다. 현재 제작팀에서 항목을 찾을 수 없다는 공통 상태와 제작팀 전환 및 해당 기능 목록 이동 수단을 제공합니다.

## 9. 비용과 정산

### REQ-08-01. 작업자 지급 비용

각 세부 작업에는 담당 작업자에게 지급할 금액을 설정할 수 있습니다.

작업자 지급 금액은 프로젝트 제작비를 구성하는 비용 중 하나이며 월간 정산의 기초 데이터로 사용합니다.

### REQ-08-02. Expense 비용 관리

YMS는 작업자 지급 금액만으로 전체 콘텐츠 제작비를 계산하지 않습니다.

권한이 있는 사용자는 별도의 Expense 비용 항목을 등록할 수 있어야 합니다.

비용 유형의 예시는 다음과 같습니다.

- 촬영 장소 및 대관료
- 장비 구매 또는 렌탈
- 출연료
- 외주 제작비
- 음원 및 라이선스 비용
- 소품 및 재료비
- 광고 집행비
- 교통 및 기타 제작 경비
- 기타

비용 유형은 향후 새로운 항목을 추가할 수 있도록 확장 가능한 구조로 설계합니다.

### REQ-08-03. 비용의 귀속 단위

Expense 항목은 성격에 따라 다음 중 하나의 단위에만 직접 귀속할 수 있어야 합니다.

- 특정 영상 프로젝트
- 특정 프로젝트 그룹
- 특정 채널
- 제작팀

하나의 Expense를 여러 대상에 동시에 직접 귀속하지 않습니다.

프로젝트 및 프로젝트 그룹의 재무 성과 계산에서는 직접 귀속된 비용만 사용하며 채널 또는 제작팀 비용을 임의로 하위 프로젝트나 프로젝트 그룹에 배분하지 않습니다.

작업자 지급 금액은 작업을 통해 프로젝트 비용에 자동으로 포함되므로 동일한 금액을 Expense로 중복 등록하여 이중 집계해서는 안 됩니다.

### REQ-08-04. 월간 정산 집계

선택한 기간을 기준으로 작업자별 지급 대상 작업과 지급 예정 금액을 자동으로 집계합니다.

취소된 프로젝트라도 이미 수행되어 지급 대상으로 인정된 작업은 정산에 포함할 수 있습니다.

### REQ-08-05. 정산 상태

정산은 다음 상태를 구분하여 관리합니다.

- DRAFT: 정산 대상과 금액을 집계 중인 상태
- CONFIRMED: 지급 대상과 금액을 확정한 상태
- PAID: 실제 지급 완료를 기록한 상태

정산 담당자는 DRAFT 상태에서 항목을 검토한 뒤 CONFIRMED 상태로 확정하고 실제 지급 후 PAID 상태로 변경할 수 있습니다.

실제 계좌이체나 결제 기능은 초기 릴리스 범위에 포함하지 않으며 YMS에서는 정산 내역과 지급 여부를 기록합니다.

### REQ-08-06. 정산 항목 스냅샷

정산이 CONFIRMED 상태가 되면 정산 대상 작업과 금액을 스냅샷으로 보존합니다.

이후 작업자 지급 금액이나 관련 설정이 변경되더라도 이미 확정된 정산 금액이 자동으로 변경되어서는 안 됩니다.

PAID 상태의 정산은 일반적인 수정 기능으로 변경할 수 없도록 제한합니다.

### REQ-08-07. 제작팀 정산 관리와 개인 정산 분리

OWNER와 ADMIN이 사용하는 제작팀 정산 관리와 MEMBER가 사용하는 개인 정산 조회는 별개의 기능으로 구현합니다.

제작팀 정산 관리는 제작팀 전체 작업자의 정산 조회, 생성, 재계산, 확정과 지급 완료 처리를 제공합니다. 개인 정산은 현재 사용자의 지급 대상 작업과 정산 상태만 조회합니다.

두 기능은 화면 Route, 화면 상태와 API 조회 로직을 분리합니다. 금액 표시, 정산 상태 배지와 기간 입력처럼 권한이나 데이터 범위를 포함하지 않는 표현 컴포넌트만 공통으로 사용할 수 있습니다.

## 10. 수익과 콘텐츠 가치 분석

### REQ-09-01. 수익원 관리

YMS는 YouTube 조회수 기반 플랫폼 수익만을 콘텐츠의 수익으로 간주하지 않습니다.

제작팀에서는 최소한 다음 수익 유형을 구분하여 기록할 수 있어야 합니다.

- YOUTUBE_PLATFORM: YouTube 광고, Premium 등 플랫폼에서 발생한 수익
- SPONSORSHIP: 브랜드 광고 및 협찬 수익
- AFFILIATE: 제휴 링크 또는 제휴 마케팅 수익
- MERCHANDISE: 자체 상품 및 굿즈 판매와 관련된 수익
- MEMBERSHIP: 멤버십 및 팬 후원 성격의 수익
- OTHER: 그 외 직접 입력한 수익

수익 유형은 향후 새로운 비즈니스 모델을 추가할 수 있도록 확장 가능한 구조로 설계합니다.

### REQ-09-02. 수익의 귀속 단위

하나의 수익 항목은 다음 중 하나의 단위에만 직접 귀속할 수 있어야 합니다.

- 특정 영상 프로젝트
- 특정 프로젝트 그룹
- 특정 채널
- 제작팀

하나의 수익을 여러 대상에 동시에 직접 귀속하지 않습니다.

특정 영상 한 편에 직접 귀속할 수 없는 협찬 계약, 굿즈 매출, 멤버십 등의 수익을 임의로 영상별 수익으로 나누도록 강제하지 않습니다.

채널 또는 제작팀에 귀속된 수익은 프로젝트나 프로젝트 그룹의 재무 성과 계산에 임의로 배분하지 않습니다.

### REQ-09-03. 수익 항목 등록

권한이 있는 사용자는 수익 항목을 직접 등록할 수 있어야 합니다.

수익 항목에는 최소한 다음 정보를 관리합니다.

- 수익 유형
- 금액
- 발생일 또는 정산 기준일
- 귀속 대상
- 설명 또는 메모

초기 릴리스에서는 외부 서비스와 자동 연동되지 않는 협찬, 제휴, 상품 판매 등의 수익을 수동으로 입력할 수 있도록 합니다.

Revenue에는 실제로 발생했거나 금액이 확정된 수익만 저장합니다. 계약 예정액, 청구, 입금 여부, 미수금과 세금계산서는 관리하지 않습니다.

### REQ-09-04. 실제 수익과 추정 수익 구분

재무 성과 계산에 사용하는 수익과 참고용 추정 수익을 명확히 구분합니다.

실제 협찬금, 실제 제휴 수익, 실제 상품 매출, 실제 YouTube Analytics 수익 등 확정되거나 실제 발생한 금액은 실제 수익으로 기록할 수 있습니다.

조회수 1회당 수익 단가로 계산한 YouTube 플랫폼 예상 수익은 추정 수익으로 관리하며 **실제 ROI 계산에는 포함하지 않습니다.**

### REQ-09-05. YouTube 게시물별 조회수 1회당 수익 단가 설정

YouTube 플랫폼 수익을 간편하게 추정하기 위해 YouTube 게시물에는 Channel의 기본 조회수 1회당 수익 단가와 별도로 해당 게시물에 적용할 단가를 저장할 수 있습니다.

YouTube 게시물 생성 또는 수익 설정 시 게시 Channel과 VideoContent의 영상 유형에 맞는 기본 조회수 1회당 수익 단가를 초기값으로 사용합니다. Channel 단가가 없으면 0원을 정상적인 기본값으로 사용하며 게시물 생성을 차단하지 않습니다.

YouTube 게시물에서는 다음 수익 설정을 선택할 수 있습니다.

- 채널 기본 단가를 기준으로 적용
- 해당 게시물에 별도 단가 적용
- 수익 창출 중지

수익 창출 중지 상태에서는 조회수가 존재하더라도 조회수 기반 예상 YouTube 플랫폼 수익을 0원으로 계산합니다.

### REQ-09-06. YouTube 게시물 수익 단가 스냅샷

적용된 조회수 1회당 수익 단가는 YouTube 게시물 자체의 스냅샷 값으로 저장합니다.

Channel의 기본 단가가 변경되어도 기존 YouTube 게시물의 적용 단가가 자동으로 바뀌어서는 안 됩니다.

YouTube 게시물의 Channel 또는 연결된 VideoContent의 영상 유형을 변경할 때 `revenueOption=DEFAULT`이면 새 Channel과 영상 유형의 기본 단가를 같은 저장 요청에서 다시 스냅샷하고 변경될 단가를 저장 전에 안내합니다. CUSTOM은 게시물별 단가를, DISABLED는 0원과 비활성 상태를 유지합니다. 게시 이력이 존재하는 데이터이므로 어떤 경우에도 별도의 저장 확인 없이 단가를 암묵적으로 변경하지 않습니다.

### REQ-09-07. 조회수 1회당 수익 단가 기반 YouTube 플랫폼 수익 추정

YouTube 플랫폼 수익의 실제 금액을 연동하지 않은 게시물에서는 사용자가 설정한 조회수 1회당 수익 단가를 이용하여 예상 수익을 계산할 수 있습니다.

예상 수익은 다음 식을 기본으로 합니다.

```text
예상 YouTube 플랫폼 수익 = 조회수 × 적용 단가(원/조회)
```

롱폼과 쇼츠는 서로 다른 기본 조회수 1회당 수익 단가를 사용할 수 있어야 합니다.

조회수 1회당 수익 단가 기반 계산값은 전체 콘텐츠 수익이 아니라 여러 수익원 중 YouTube 플랫폼 수익의 **참고용 추정값**으로 취급합니다.

### REQ-09-08. 영상 결과물과 YouTube 게시물 관리

VideoContent에는 YouTube 영상 ID 또는 영상 URL로 하나 이상의 YouTubePublication을 등록할 수 있어야 합니다. URL 입력은 HTTP·HTTPS의 명시적으로 허용된 YouTube 호스트와 `watch`, `shorts`, `youtu.be` 형식만 허용하며 다른 호스트에서 추출한 11자리 값은 YouTube 영상으로 간주하지 않습니다. 같은 영상 결과물을 수정하여 다시 게시한 경우 기존 게시물을 삭제하지 않고 새 게시물을 추가하며 필요하면 `supersededByPublicationId`로 대체 관계를 기록합니다.

하나의 YouTube Video ID는 같은 Workspace에서 하나의 YouTubePublication으로만 등록할 수 있습니다. 게시물 등록 후 YouTube Data API를 이용하여 조회수 등 공개 가능한 영상 통계를 가져올 수 있도록 합니다.

조회수, 좋아요 등 콘텐츠 반응 지표는 재무 성과와 구분하여 콘텐츠 성과 지표로 관리합니다.

YouTubePublication의 내부 생명주기는 다음과 같이 관리하며 YouTube의 공개·일부 공개·비공개 설정과 구분합니다.

- CURRENT(게시 중): 해당 VideoContent와 Channel에서 현재 운영 대상으로 취급하는 게시물
- SUPERSEDED(대체됨): 같은 VideoContent와 Channel의 새 게시물로 교체된 게시물
- REMOVED(게시 종료): 현재 운영과 동기화 대상에서 제외된 게시물

하나의 VideoContent는 서로 다른 Channel에 CURRENT 게시물을 각각 가질 수 있지만 같은 Channel에는 CURRENT를 최대 하나만 가질 수 있습니다. 대체 관계는 같은 Workspace, VideoContent와 Channel 안에서만 허용하고 자기 참조와 순환 관계를 차단합니다. `supersededByPublicationId`가 전달되면 현재 VideoContent와 Channel의 CURRENT 게시물과 정확히 일치해야 하며, CURRENT가 없거나 다른 ID이면 등록을 거부합니다. 같은 Channel에 CURRENT 게시물이 있으면 새 게시물이 기존 게시물을 대체한다는 사용자의 명시적 확인 없이 상태를 변경하지 않습니다.

REMOVED 사유는 최소한 UNAVAILABLE과 INCORRECT를 구분합니다. UNAVAILABLE은 과거에는 유효했으나 외부 삭제나 운영 종료 등으로 사용할 수 없는 게시물이며 누적 성과에 포함합니다. INCORRECT는 잘못 연결한 게시물이며 현재·누적 집계에서 모두 제외합니다.

SUPERSEDED와 REMOVED 게시물은 사용자의 명시적 복원 동작으로 CURRENT가 될 수 있습니다. 같은 Channel에 다른 CURRENT가 있으면 이를 대체할지 다시 확인하고 상태 전환, 대체 관계 변경과 이력 기록을 하나의 트랜잭션에서 처리합니다. 게시물 상태, 종료 사유와 대체 관계의 모든 변경은 전용 생명주기 이력으로 보존합니다.

외부 API가 영상을 찾지 못하거나 동기화에 실패했다는 이유만으로 생명주기 상태를 자동 변경하지 않습니다. 기존 상태와 마지막 성공 데이터를 유지하고 확인 필요 상태를 표시하며, 사용자가 확인한 뒤 게시 종료 사유를 선택하도록 합니다.

### REQ-09-08-1. 현재 성과와 누적 게시 성과

VideoContent, 대표 Project와 ProjectGroup에는 현재 성과와 누적 게시 성과를 구분하여 제공합니다.

- 현재 성과: CURRENT 게시물의 마지막 성공 성과 합계
- 누적 게시 성과: CURRENT, SUPERSEDED와 REMOVED / UNAVAILABLE 게시물의 마지막 성공 성과 합계
- REMOVED / INCORRECT 게시물: 모든 집계에서 제외

조회수, 좋아요, 댓글과 예상 플랫폼 수익에 같은 게시물 포함 기준을 적용합니다. 합계는 여러 게시물의 단순 합계이며 고유 시청자나 고유 반응 사용자 수를 의미하지 않습니다. 예상 플랫폼 수익은 각 게시물의 조회수와 해당 게시물의 적용 단가를 먼저 곱한 뒤 합산합니다.

성공한 동기화 데이터가 없는 게시물은 0으로 간주하지 않고 미집계로 처리합니다. 마지막 성공값은 합계에 포함하되 게시물별 마지막 성공 시각, 마지막 시도 실패 여부와 집계의 완전·일부 미집계·전체 미집계 상태를 함께 제공합니다. 초기에는 임의의 데이터 만료 기간을 두지 않습니다.

Project와 VideoContent 목록은 현재 성과를 기본으로 표시하고 Project 상세에서는 현재·누적 성과를 함께 제공합니다. ProjectGroup과 분석 화면은 누적 게시 성과를 주 지표, 현재 성과를 보조 지표로 사용합니다. YouTubePublication 목록은 합계 대신 게시물별 자체 성과를 표시합니다.

### REQ-09-09. 실제 YouTube 수익 데이터 연동

YouTube Analytics API는 OAuth 인증을 통해 채널 소유자의 분석 데이터를 조회할 수 있으며 별도의 금전 데이터 조회 권한을 승인받으면 estimatedRevenue 등 수익 관련 지표를 조회할 수 있습니다.

초기 릴리스에서는 Google 계정 및 민감한 수익 데이터 권한 승인을 필수로 요구하지 않기 위해 사용자가 설정한 조회수 1회당 수익 단가 기반 추정 기능을 제공합니다.

향후 사용자가 명시적으로 OAuth 권한을 승인한 경우 실제 YouTube Analytics 수익 데이터를 선택적으로 연동할 수 있도록 확장합니다.

참고:

- [YouTube Analytics API - Reports Query](https://developers.google.com/youtube/analytics/reference/reports/query)
- [YouTube Data API - Videos](https://developers.google.com/youtube/v3/docs/videos)

### REQ-09-10. 프로젝트 재무 성과

프로젝트의 재무 성과는 해당 프로젝트에 직접 귀속된 **실제 비용과 실제 수익**만을 이용하여 계산합니다.

프로젝트 비용에는 다음 항목을 포함합니다.

- 프로젝트 작업에 연결된 작업자 지급 금액
- 프로젝트에 직접 귀속된 Expense

프로젝트 실제 수익에는 프로젝트에 직접 귀속된 실제 Revenue만 포함합니다.

기본 재무 지표는 다음과 같습니다.

```text
손익 = 실제 수익 - 실제 비용

ROI = (실제 수익 - 실제 비용) ÷ 실제 비용 × 100

수익/비용 배수 = 실제 수익 ÷ 실제 비용
```

조회수, 좋아요와 조회수 1회당 수익 단가 기반 추정 수익은 실제 ROI 계산에 포함하지 않습니다.

### REQ-09-11. 프로젝트 그룹 재무 성과

프로젝트 그룹의 재무 성과는 다음 항목을 집계하여 계산합니다.

#### 비용

- 프로젝트 그룹에 직접 귀속된 Expense
- 프로젝트 그룹에 속한 프로젝트의 작업자 지급 금액
- 프로젝트 그룹에 속한 프로젝트에 직접 귀속된 Expense

#### 실제 수익

- 프로젝트 그룹에 직접 귀속된 실제 Revenue
- 프로젝트 그룹에 속한 프로젝트에 직접 귀속된 실제 Revenue

채널 또는 제작팀에 직접 귀속된 비용과 수익은 프로젝트 그룹에 임의로 배분하지 않습니다.

프로젝트 그룹에서도 실제 비용과 실제 수익을 기준으로 손익, ROI와 수익/비용 배수를 제공합니다.

### REQ-09-12. 콘텐츠 성과와 재무 성과 분리

조회수, 좋아요, 댓글 등 콘텐츠 반응 지표는 콘텐츠 성과로 별도 표시합니다.

재무 성과 화면에서는 실제 금액을 이용한 손익과 ROI를 우선 표시하며 조회수 등은 왜 해당 결과가 발생했는지 판단하는 참고 지표로 함께 제공합니다.

개별 영상의 조회수가 높다는 이유만으로 성공한 프로젝트로 판단하거나 조회수를 임의의 금전 가치로 환산하지 않습니다.

수익을 특정 프로젝트에 직접 귀속할 수 없는 경우에도 이를 임의 배분하지 않고 프로젝트 그룹, 채널 또는 제작팀 수준에 그대로 보존합니다.

### REQ-09-13. 외부 데이터 갱신 실패 처리

YouTube API 호출이 실패하거나 할당량 제한 등으로 데이터를 갱신할 수 없는 경우 기존에 저장된 마지막 성공 데이터를 유지합니다.

화면에서는 마지막 데이터 갱신 시각과 현재 갱신 실패 여부를 사용자가 확인할 수 있어야 합니다.

## 11. 비기능 요구사항

### NFR-01. 인증 및 접근 제어

인증이 필요한 API는 로그인한 사용자만 접근할 수 있어야 합니다.

제작팀 및 프로젝트 리소스는 서버에서 권한을 다시 검증해야 하며 클라이언트 화면의 노출 여부만으로 접근 권한을 제어해서는 안 됩니다.

특히 재무 정보는 일반 프로젝트 접근 권한과 별도로 제작팀 권한을 확인해야 합니다.

### NFR-02. 입력값 검증과 오류 응답

클라이언트와 서버 양쪽에서 필요한 입력값을 검증합니다.

서버 API는 오류 유형을 구분할 수 있는 일관된 오류 코드와 메시지를 반환해야 합니다.

인증 만료, 권한 부족, 잘못된 입력, 존재하지 않는 리소스와 서버 오류를 구분하여 처리합니다.

### NFR-03. 금액 계산 정확성

작업자 지급액, Expense, Revenue, 조회수 1회당 수익 단가, 예상 수익과 정산 금액은 부동소수점 오차가 발생하지 않는 자료형과 계산 방식을 사용합니다.

백엔드에서는 금액 계산에 `BigDecimal` 사용을 기본으로 합니다.

### NFR-04. 목록 데이터 조회 성능

프로젝트, 작업, 채팅, 알림, 비용과 수익 등 지속적으로 데이터가 증가하는 목록은 전체 데이터를 한 번에 반환하지 않도록 페이지네이션 또는 커서 기반 조회를 지원합니다.

### NFR-05. 외부 API 의존성 분리

YouTube API 장애 또는 미연동 상태에서도 프로젝트, 일정, 채팅, 비용, 정산 등 YMS의 핵심 업무 기능은 사용할 수 있어야 합니다.

외부 데이터는 마지막 정상 조회 결과와 갱신 상태를 구분하여 관리합니다.

### NFR-06. 동시 수정 처리

여러 사용자가 동일한 프로젝트, 작업, 비용, 수익 또는 정산 데이터를 동시에 수정할 수 있음을 고려합니다.

중요 데이터가 마지막 요청에 의해 조용히 덮어써지지 않도록 버전 관리, 낙관적 잠금 등 동시성 제어 방식을 데이터 및 API 설계 단계에서 결정합니다.

### NFR-07. 시간 정보

날짜와 일시를 명확히 구분합니다.

업로드 일시, 메시지 작성 시각, 알림 시각 등 실제 시점이 중요한 데이터는 서버에서 일관된 기준으로 저장하고 사용자 화면에서 적절한 지역 시간으로 표시합니다.

### NFR-08. 반응형 UI

주요 화면은 데스크톱과 모바일 환경에서 사용할 수 있어야 합니다.

특히 일정 확인, 알림, 채팅, 작업 상태 변경과 개인 정산 확인은 모바일 환경에서도 핵심 기능을 수행할 수 있어야 합니다.

큰 화면과 모바일 화면은 사용자가 이미 익힌 위치와 순서를 바탕으로 같은 기능을 찾을 수 있도록 동일한 조작 체계를 공유해야 합니다.

화면 폭이 좁아졌다는 이유로 주요 내비게이션을 별도의 햄버거 메뉴나 Drawer 안으로 옮기지 않습니다. 공통 헤더의 메뉴 순서, 아이콘, 이름과 활성 상태를 유지하고, 모바일에서는 같은 메뉴 행을 가로로 탐색할 수 있게 합니다. 현재 메뉴는 화면 안에서 확인할 수 있도록 필요한 경우 자동으로 노출 위치를 조정합니다.

## 13. 초기 릴리스 제외 범위

다음 기능은 초기 릴리스에서 직접 구현하지 않습니다.

- 실제 영상 파일 업로드 및 영상 편집 기능
- 작업자에게 실제 금액을 송금하는 결제 또는 계좌이체 기능
- YouTube Studio를 대체하는 채널 관리 기능
- Google OAuth를 이용한 실제 YouTube 수익 데이터 연동
- 상위 단위 비용 또는 수익을 하위 프로젝트에 자동 배분하는 기능
- 모바일 전용 네이티브 애플리케이션

외부 매출 시스템의 완전한 자동 연동보다 수동 입력과 YouTube 기본 데이터 연동을 우선하여 실제 사용 가능한 범위를 확보하고 이후 사용자 피드백에 따라 확장합니다.
