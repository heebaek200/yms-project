# 요구사항

> YMS(YouTube Management System)의 기능 및 비기능 요구사항을 정의합니다.  
> 본 문서는 초기 블로그 설계를 현재 구현 상태와 실제 배포 가능한 SaaS 구조에 맞게 재정리한 문서입니다.

## 1. 프로젝트 개요

### 1.1. 배경

YMS는 유튜브 채널을 운영하면서 여러 영상 편집자와 썸네일 작업자를 관리하는 미디어 에이전시를 가상의 클라이언트로 설정하여 기획한 서비스입니다.

현재 영상 제작 업무에서 카카오톡, 노션, 구글 스프레드시트 등에 분산되어 관리되는 일정, 작업 배정, 커뮤니케이션, 제작비 정산과 영상 성과 데이터를 하나의 웹 시스템에서 통합 관리하는 것을 목표로 합니다.

### 1.2. 핵심 목표

YMS의 핵심 가치는 **콘텐츠 제작에 투입한 비용으로부터 얼마의 가치를 만들었는지 관리하는 것**입니다.

- 영상 제작 일정과 작업 진행 상태를 관리합니다.
- 워크스페이스를 중심으로 채널과 참여자를 관리합니다.
- 여러 콘텐츠 프로젝트를 하나의 캠페인으로 묶어 관리할 수 있습니다.
- 사용자 전문 역할, 워크스페이스 권한, 프로젝트 권한을 구분하여 접근을 제어합니다.
- 프로젝트별 실시간 소통과 알림을 제공합니다.
- 작업자별 제작비와 월간 정산을 관리합니다.
- YouTube 플랫폼 수익뿐 아니라 광고·협찬·제휴·상품 판매 등 다양한 수익원을 기록합니다.
- 프로젝트와 캠페인 단위로 제작비 대비 수익과 성과를 분석합니다.
- 초기 릴리스 이후 실제 사용자를 받을 수 있는 서비스로 확장 가능한 구조를 지향합니다.

### 1.3. 권한 개념

YMS에서는 역할과 권한을 다음 세 가지 범위로 구분합니다.

| 구분 | 값 | 의미 |
| --- | --- | --- |
| 전문 역할 | CREATOR, EDITOR, THUMBNAILER | 사용자가 수행할 수 있는 업무 |
| 워크스페이스 권한 | OWNER, ADMIN, MEMBER | 조직 또는 팀 안에서의 관리 권한 |
| 프로젝트 권한 | EDIT, VIEW | 특정 프로젝트에 대한 접근 권한 |

한 사용자는 여러 전문 역할을 동시에 가질 수 있으며 여러 워크스페이스에 서로 다른 권한으로 참여할 수 있습니다.

프로젝트를 생성한 사용자는 해당 프로젝트의 소유자가 되며, 프로젝트 참여자에게 EDIT 또는 VIEW 권한을 부여할 수 있습니다.

## 2. 회원과 프로필

### REQ-01-01. 회원가입 및 로그인

사용자는 이메일과 비밀번호를 이용하여 회원가입하고 로그인할 수 있어야 합니다.

인증에 성공한 사용자는 자신의 워크스페이스, 프로젝트, 일정과 알림 정보에 접근할 수 있습니다.

### REQ-01-02. 다중 전문 역할 지원

사용자는 다음 전문 역할을 하나 이상 선택할 수 있습니다.

- CREATOR: 채널 운영자 또는 기획자
- EDITOR: 영상 편집자
- THUMBNAILER: 썸네일 작업자

한 사람이 여러 업무를 담당할 수 있으므로 복수 선택을 허용합니다.

### REQ-01-03. 프로필 및 역할 정보 관리

사용자는 회원가입 이후 프로필 설정 화면에서 이름 또는 닉네임과 전문 역할을 설정하고 수정할 수 있습니다.

작업 담당자를 선택할 때는 해당 작업에 적합한 전문 역할을 가진 사용자를 우선적으로 조회할 수 있어야 합니다.

### REQ-01-04. 크리에이터 기본 RPM 설정

CREATOR 역할을 가진 사용자는 프로필에 다음 기본 RPM을 설정할 수 있습니다.

- 롱폼 기본 RPM
- 쇼츠 기본 RPM

프로필의 RPM은 새로운 프로젝트의 예상 수익 설정에 사용할 **기본값**입니다.

프로필의 기본 RPM을 변경하더라도 이미 프로젝트에 저장된 RPM 값이 자동으로 변경되어서는 안 됩니다. 사용자가 기존 미확정 프로젝트에도 변경값을 적용하도록 명시적으로 선택한 경우에만 일괄 변경할 수 있습니다.

확정된 정산 또는 성과 기준에 사용된 값은 변경 대상에서 제외합니다.

## 3. 워크스페이스와 멤버

### REQ-02-01. 워크스페이스 생성

사용자는 하나 이상의 워크스페이스를 생성할 수 있습니다.

워크스페이스는 미디어 에이전시, 제작팀 또는 개인 채널 운영 조직을 나타내며 채널, 프로젝트, 멤버와 정산 정보를 관리하는 최상위 업무 단위입니다.

워크스페이스를 생성한 사용자는 해당 워크스페이스의 OWNER 권한을 가집니다.

### REQ-02-02. 워크스페이스 권한

워크스페이스에는 다음 권한을 사용합니다.

- OWNER: 워크스페이스 전체 관리, 관리자 지정, 소유권 이전 및 삭제 가능
- ADMIN: 멤버, 채널, 프로젝트 등 주요 업무 정보 관리 가능
- MEMBER: 참여 중인 프로젝트와 자신에게 허용된 업무 기능 사용 가능

OWNER 권한은 워크스페이스마다 최소 한 명이 존재해야 합니다.

### REQ-02-03. 멤버 초대

OWNER 또는 ADMIN은 이메일을 이용하여 사용자를 워크스페이스에 초대할 수 있습니다.

초대에는 다음 상태를 관리합니다.

- 초대 대기
- 수락
- 거절
- 취소

이미 YMS 회원인 사용자는 로그인 후 초대를 확인하여 수락하거나 거절할 수 있어야 합니다.

아직 회원이 아닌 이메일을 초대한 경우 회원가입 후 해당 초대를 이어서 처리할 수 있도록 설계합니다.

OWNER 또는 ADMIN은 수락되지 않은 초대를 취소하거나 다시 보낼 수 있어야 합니다.

### REQ-02-04. 멤버 관리

OWNER 또는 ADMIN은 워크스페이스 멤버 목록과 각 멤버의 전문 역할 및 워크스페이스 권한을 확인할 수 있습니다.

권한이 있는 사용자는 MEMBER를 워크스페이스에서 제외할 수 있습니다.

OWNER의 권한 변경 또는 탈퇴가 필요한 경우 먼저 다른 멤버에게 소유권을 이전해야 합니다.

## 4. 채널 관리

### REQ-03-01. 워크스페이스별 채널 등록

워크스페이스에는 하나 이상의 YouTube 채널을 등록할 수 있습니다.

채널에는 최소한 다음 정보를 관리합니다.

- 채널명
- YouTube 채널 ID 또는 채널 URL
- 채널 설명
- YouTube 연동 상태

초기에는 YouTube 계정 연동 없이 채널 정보를 수동으로 등록할 수 있어야 합니다.

### REQ-03-02. 채널과 프로젝트 연결

모든 영상 프로젝트는 워크스페이스에 등록된 하나의 채널과 연결할 수 있습니다.

프로젝트 생성 시 채널을 지정하면 해당 채널을 기준으로 일정과 영상 성과를 조회할 수 있어야 합니다.

하나의 채널에는 여러 캠페인과 영상 프로젝트가 존재할 수 있습니다.

### REQ-03-03. YouTube 채널 연동

사용자는 필요한 경우 Google OAuth를 통해 자신이 권한을 가진 YouTube 채널을 YMS와 연결할 수 있습니다.

연동이 해제되더라도 기존 프로젝트와 YMS 내부 데이터는 유지되어야 하며, 외부 API를 통해 새 데이터를 갱신하는 기능만 제한합니다.

## 5. 캠페인 관리

### REQ-08-01. 캠페인 생성

권한이 있는 사용자는 하나의 비즈니스 목적이나 계약으로 묶이는 여러 콘텐츠를 관리하기 위해 캠페인을 생성할 수 있습니다.

캠페인의 예시는 다음과 같습니다.

- 브랜드 협찬 캠페인
- 신제품 출시 프로모션
- 특정 상품의 제휴 마케팅
- 자체 굿즈 출시
- 시즌 또는 이벤트 콘텐츠 묶음

캠페인에는 최소한 다음 정보를 관리합니다.

- 캠페인명
- 담당 채널
- 설명
- 시작일
- 종료일
- 상태

### REQ-08-02. 캠페인과 프로젝트 연결

하나의 캠페인에는 여러 영상 프로젝트를 연결할 수 있습니다.

예를 들어 하나의 브랜드 계약에 롱폼 영상 2편과 쇼츠 3편이 포함되어 있다면 각 콘텐츠는 별도의 영상 프로젝트로 관리하고, 동일한 캠페인에 연결할 수 있어야 합니다.

영상 프로젝트는 캠페인 없이 독립적으로 생성할 수도 있어야 합니다.

### REQ-08-03. 캠페인 단위 비용과 수익 집계

캠페인에 연결된 프로젝트의 제작비와 캠페인에 귀속된 수익을 합산하여 캠페인 전체의 비용과 수익을 조회할 수 있어야 합니다.

캠페인 단위 분석은 개별 영상의 조회수만으로 콘텐츠의 비즈니스 가치를 판단하지 않고, 여러 콘텐츠가 공동으로 수행한 광고·협찬·판매 등의 성과를 함께 평가하기 위한 기능입니다.

### REQ-08-04. 캠페인 상태 관리

캠페인은 최소한 다음 상태를 구분하여 관리합니다.

- PLANNING: 준비 중
- ACTIVE: 진행 중
- COMPLETED: 완료
- CANCELLED: 취소

완료 또는 취소된 캠페인의 프로젝트, 비용과 수익 이력은 보존해야 합니다.

## 6. 프로젝트와 작업 관리

### REQ-08-01. 영상 프로젝트 생성

권한이 있는 사용자는 다음 정보를 입력하여 영상 프로젝트를 생성할 수 있습니다.

- 프로젝트 제목
- 기획 내용
- 담당 채널
- 프로젝트 상태
- 제작 마감일
- 업로드 예정일

프로젝트를 생성한 사용자는 해당 프로젝트의 소유자가 됩니다.

### REQ-08-02. 프로젝트 일정 구분

영상 프로젝트에서는 다음 일정을 서로 구분하여 관리합니다.

- 제작 마감일(due date): 편집, 썸네일 등 제작 작업을 완료해야 하는 기준일
- 업로드 예정일(planned upload date): 영상을 공개할 계획인 날짜
- 실제 업로드 일시(uploaded at): 영상이 실제로 업로드 또는 공개된 일시

실제 업로드 일시는 YouTube 연동을 통해 가져오거나 사용자가 직접 입력할 수 있습니다.

### REQ-08-03. 프로젝트 참여자와 권한

프로젝트 소유자 또는 권한이 있는 사용자는 워크스페이스 멤버를 프로젝트 참여자로 추가할 수 있습니다.

참여자에게는 다음 프로젝트 권한을 부여합니다.

- EDIT: 프로젝트 조회 및 수정, 작업 관리와 협업 기능 사용 가능
- VIEW: 프로젝트 및 관련 정보를 조회할 수 있으나 변경할 수 없음

프로젝트 참여자가 아니거나 필요한 권한이 없는 사용자의 접근은 차단합니다.

### REQ-08-04. 프로젝트 상태 관리

프로젝트는 기본적으로 다음 진행 상태를 가집니다.

- PLANNING: 기획 단계
- EDITING: 제작 진행 중
- REVIEW: 검수 중
- UPLOADED: 업로드 완료
- CANCELLED: 제작 취소

세부 작업의 상태에 따라 프로젝트 상태를 자동으로 변경할 수 있습니다.

권한이 있는 사용자는 필요한 경우 프로젝트 상태를 직접 변경할 수 있습니다.

### REQ-08-05. 프로젝트 취소

더 이상 제작하지 않는 프로젝트는 삭제하지 않고 CANCELLED 상태로 변경할 수 있습니다.

취소된 프로젝트는 기본 진행 목록에서 제외하되 이력, 작업 비용, 채팅 등 기존 데이터는 유지합니다.

이미 발생한 제작 비용이 있는 경우 취소 프로젝트도 정산 대상에 포함할 수 있어야 합니다.

### REQ-08-06. 프로젝트 보관

완료되었거나 취소된 프로젝트는 보관(archive)할 수 있습니다.

보관된 프로젝트는 기본 프로젝트 목록과 일정 화면에서 제외하지만 별도의 보관 목록에서 조회할 수 있어야 합니다.

보관 상태는 해제할 수 있어야 하며 프로젝트의 업무 상태와는 별도로 관리합니다.

### REQ-08-07. 프로젝트 삭제

프로젝트 소유자 또는 충분한 관리 권한을 가진 사용자만 프로젝트 삭제를 요청할 수 있습니다.

삭제 전 사용자에게 확인 절차를 제공해야 하며 삭제된 프로젝트는 일반 사용자 화면, 검색, 일정 및 통계에서 제외합니다.

실제 데이터의 물리 삭제 여부와 보존 기간은 데이터베이스 및 운영 정책 설계 단계에서 별도로 결정합니다.

### REQ-08-08. 세부 작업 등록

하나의 영상 프로젝트에는 여러 세부 작업을 등록할 수 있습니다.

각 작업에는 다음 정보를 관리합니다.

- 작업 종류
- 담당자
- 시작일
- 종료일
- 제작 비용
- 작업 상태

### REQ-08-09. 확장 가능한 작업 종류

시스템은 기본 작업 종류를 제공하되 특정 종류만 코드에 고정하지 않는 확장 가능한 구조로 설계합니다.

기본 작업 종류의 예시는 다음과 같습니다.

- 가편집
- 종합 편집
- 자막
- 썸네일

향후 촬영, 모션그래픽, 번역, 더빙, 쇼츠 재가공 등 새로운 작업 종류를 추가할 수 있어야 합니다.

워크스페이스에서 사용자 정의 작업 종류를 추가하거나 사용하지 않는 작업 종류를 비활성화할 수 있도록 확장 가능하게 설계합니다.

기존 프로젝트에서 사용된 작업 종류를 비활성화하더라도 과거 작업 이력은 유지되어야 합니다.

### REQ-08-10. 작업 상태 관리

작업자는 자신에게 배정된 작업의 진행 상태를 다음 순서로 변경할 수 있습니다.

대기 → 진행 중 → 검수 요청 → 완료

시스템 내부 상태는 다음 값을 기본으로 사용합니다.

- WAITING
- PROGRESS
- REVIEW
- COMPLETED

프로젝트 소유자 또는 EDIT 권한을 가진 사용자는 필요한 경우 작업 상태를 조정할 수 있습니다.

### REQ-08-11. 캘린더 기반 일정 조회

프로젝트와 작업 일정은 메인 대시보드 또는 스케줄러 화면에서 달력 형태로 확인할 수 있어야 합니다.

기간이 있는 작업은 달력 위에서 시작일부터 종료일까지 이어지는 일정으로 표시합니다.

사용자는 일정이 겹치는 작업과 특정 작업자에게 집중된 업무를 쉽게 파악할 수 있어야 합니다.

### REQ-08-12. 일정 필터와 검색

스케줄러에서는 다음 조건을 조합하여 일정을 조회할 수 있어야 합니다.

- 조회 기간
- 프로젝트 상태
- 담당 전문 역할
- 내가 담당한 작업
- 프로젝트 또는 작업 관련 키워드

워크스페이스에 여러 채널이 등록된 경우 채널을 기준으로 일정을 필터링할 수 있도록 확장합니다.

## 7. 프로젝트 채팅과 알림

### REQ-08-01. 프로젝트별 채팅방

영상 프로젝트가 생성되면 해당 프로젝트 전용 채팅 공간을 사용할 수 있어야 합니다.

프로젝트 소유자와 참여자만 채팅방에 접근할 수 있으며 권한이 없는 사용자의 접근은 차단합니다.

### REQ-08-02. 실시간 메시지 송수신

프로젝트 채팅 메시지는 화면을 새로고침하지 않아도 실시간으로 전송되고 표시되어야 합니다.

실시간 통신은 WebSocket 기반으로 구현하는 것을 기본 방향으로 합니다.

### REQ-08-03. 대화 이력 보존

모든 채팅 메시지는 데이터베이스에 저장합니다.

사용자가 채팅방에 다시 입장하면 최근 메시지를 우선 조회하고 이전 메시지는 추가로 불러올 수 있어야 합니다.

메시지가 많아지는 경우를 고려하여 페이지 또는 커서 단위 조회가 가능해야 합니다.

### REQ-08-04. 읽지 않은 메시지

사용자별로 프로젝트 채팅의 마지막 확인 위치를 관리합니다.

사용자는 프로젝트별 읽지 않은 메시지 수를 확인할 수 있어야 하며 채팅방을 확인하면 읽음 상태가 갱신되어야 합니다.

### REQ-08-05. 알림 제공

사용자에게 자신과 관련된 주요 변경 사항을 알림으로 제공합니다.

초기 알림 대상에는 최소한 다음 이벤트를 포함합니다.

- 자신에게 배정된 작업의 변경
- 작업 상태 변경 및 검수 요청
- 참여 중인 프로젝트의 새 채팅 메시지
- 워크스페이스 초대

향후 정산 확정 등 다른 이벤트를 추가할 수 있도록 알림 유형을 확장 가능한 구조로 설계합니다.

### REQ-08-06. 알림 조회 및 읽음 처리

사용자는 전체 알림과 읽지 않은 알림을 조회할 수 있어야 합니다.

시스템은 읽지 않은 알림 수를 제공하고, 사용자가 알림을 확인하면 읽음 상태를 기록합니다.

알림 목록은 최근 항목부터 조회하며 조회 개수를 제한할 수 있어야 합니다.

## 8. 대시보드와 성과 조회

### REQ-08-01. 대시보드 요약 카드

사용자는 워크스페이스의 현재 업무 상태를 빠르게 확인할 수 있도록 다음 요약 정보를 카드 형태로 확인할 수 있어야 합니다.

- 진행 중 프로젝트 수
- 내가 담당한 마감 예정 작업 수
- 검수 요청 중인 작업 수
- 마감 임박 작업 수

각 요약 카드는 관련 프로젝트 또는 작업 목록으로 이동할 수 있도록 확장합니다.

### REQ-08-02. 프로젝트 진척률

진행 중인 전체 프로젝트의 상태 비율을 차트로 표시합니다.

각 프로젝트에서는 완료된 세부 작업과 전체 세부 작업의 비율을 이용하여 진척률을 계산하고 진행 바로 표시합니다.

### REQ-08-03. 작업자별 업무량

작업자별로 배정된 작업 수와 진행 중인 작업 수를 비교할 수 있어야 합니다.

특정 작업자에게 업무가 집중되었는지 확인할 수 있도록 시각화하고 새로운 작업을 배정할 때 참고할 수 있도록 합니다.

### REQ-08-04. 영상별 제작비 대비 성과

업로드가 완료된 프로젝트에 실제 YouTube 영상 ID를 연결할 수 있습니다.

시스템은 조회수와 프로젝트 제작비, 예상 또는 연동된 수익 데이터를 이용하여 영상별 성과를 비교할 수 있어야 합니다.

단순 조회수뿐 아니라 제작비 대비 효율을 함께 확인할 수 있도록 그래프와 요약 지표를 제공합니다.

## 9. 제작비와 정산

### REQ-08-01. 작업별 제작 비용

각 세부 작업에는 작업자에게 지급할 제작 비용을 설정할 수 있습니다.

금액은 정수형 부동소수점 계산이 아닌 정확한 금액 계산이 가능한 방식으로 처리해야 합니다.

### REQ-08-02. 월간 정산 집계

선택한 기간을 기준으로 작업자별 지급 대상 작업과 지급 예정 금액을 자동으로 집계합니다.

취소된 프로젝트라도 이미 수행되어 지급 대상으로 인정된 작업은 정산에 포함할 수 있습니다.

### REQ-08-03. 정산 상태

정산은 다음 상태를 구분하여 관리합니다.

- DRAFT: 정산 대상과 금액을 집계 중인 상태
- CONFIRMED: 지급 대상과 금액을 확정한 상태
- PAID: 실제 지급 완료를 기록한 상태

정산 담당자는 DRAFT 상태에서 항목을 검토한 뒤 CONFIRMED 상태로 확정하고 실제 지급 후 PAID 상태로 변경할 수 있습니다.

실제 계좌이체나 결제 기능은 초기 릴리스 범위에 포함하지 않으며 YMS에서는 정산 내역과 지급 여부를 기록합니다.

### REQ-08-04. 정산 항목 스냅샷

정산이 CONFIRMED 상태가 되면 정산 대상 작업과 금액을 스냅샷으로 보존합니다.

이후 작업의 기본 비용이나 관련 설정이 변경되더라도 이미 확정된 정산 금액이 자동으로 변경되어서는 안 됩니다.

PAID 상태의 정산은 일반적인 수정 기능으로 변경할 수 없도록 제한합니다.

## 10. 수익과 콘텐츠 가치 분석

### REQ-09-01. 수익원 관리

YMS는 YouTube 조회수 기반 플랫폼 수익만을 콘텐츠의 수익으로 간주하지 않습니다.

워크스페이스에서는 최소한 다음 수익 유형을 구분하여 기록할 수 있어야 합니다.

- YOUTUBE_PLATFORM: YouTube 광고, Premium 등 플랫폼에서 발생한 수익
- SPONSORSHIP: 브랜드 광고 및 협찬 수익
- AFFILIATE: 제휴 링크 또는 제휴 마케팅 수익
- MERCHANDISE: 자체 상품 및 굿즈 판매와 관련된 수익
- MEMBERSHIP: 멤버십 및 팬 후원 성격의 수익
- OTHER: 그 외 직접 입력한 수익

수익 유형은 향후 새로운 비즈니스 모델을 추가할 수 있도록 확장 가능한 구조로 설계합니다.

### REQ-09-02. 수익의 귀속 단위

수익 항목은 성격에 따라 다음 단위에 귀속할 수 있어야 합니다.

- 특정 영상 프로젝트
- 특정 캠페인
- 특정 채널
- 워크스페이스

특정 영상 한 편에 직접 귀속할 수 없는 협찬 계약, 굿즈 매출, 멤버십 등의 수익을 임의로 영상별 수익으로 나누도록 강제하지 않습니다.

분석 화면에서는 직접 귀속된 수익과 상위 단위에 귀속된 수익을 구분하여 표시해야 합니다.

### REQ-09-03. 수익 항목 등록

권한이 있는 사용자는 수익 항목을 직접 등록할 수 있어야 합니다.

수익 항목에는 최소한 다음 정보를 관리합니다.

- 수익 유형
- 금액
- 발생일 또는 정산 기준일
- 귀속 대상
- 설명 또는 메모
- 실제 금액 여부

초기 릴리스에서는 외부 서비스와 자동 연동되지 않는 협찬, 제휴, 상품 판매 등의 수익을 수동으로 입력할 수 있도록 합니다.

### REQ-09-04. 프로젝트별 RPM 설정

YouTube 플랫폼 수익을 간편하게 추정하기 위해 프로젝트에는 프로필의 기본 RPM과 별도로 해당 영상에 적용할 RPM 정보를 저장할 수 있습니다.

프로젝트 생성 또는 수익 설정 시 CREATOR 프로필의 롱폼 또는 쇼츠 기본 RPM을 초기값으로 사용할 수 있습니다.

프로젝트에서는 다음 수익 설정을 선택할 수 있습니다.

- 프로필 기본 RPM을 기준으로 적용
- 해당 프로젝트에 별도 RPM 적용
- 수익 창출 중지

수익 창출 중지 상태에서는 조회수가 존재하더라도 RPM 기반 예상 YouTube 플랫폼 수익을 0원으로 계산합니다.

### REQ-09-05. 프로젝트 RPM 스냅샷

프로젝트에 적용된 RPM은 프로젝트 자체의 스냅샷 값으로 저장합니다.

프로필의 기본 RPM이 변경되어도 기존 프로젝트의 RPM이 자동으로 바뀌어서는 안 됩니다.

사용자가 기존 미확정 프로젝트에 새 기본값을 일괄 적용하도록 명시적으로 요청한 경우에만 갱신할 수 있습니다.

성과 또는 정산 기준으로 확정된 프로젝트의 RPM 스냅샷은 자동 갱신 대상에서 제외합니다.

### REQ-09-06. RPM 기반 YouTube 플랫폼 수익 추정

YouTube 플랫폼 수익의 실제 금액을 연동하지 않은 프로젝트에서는 사용자가 설정한 RPM을 이용하여 예상 수익을 계산할 수 있습니다.

예상 수익은 다음 식을 기본으로 합니다.

```text
예상 YouTube 플랫폼 수익 = 조회수 ÷ 1,000 × 적용 RPM
```

롱폼과 쇼츠는 서로 다른 기본 RPM을 사용할 수 있어야 합니다.

RPM 기반 계산값은 전체 콘텐츠 수익이 아니라 **여러 수익원 중 YouTube 플랫폼 수익의 추정값**으로 취급합니다.

### REQ-09-07. YouTube 영상 데이터 연결

업로드된 프로젝트에는 YouTube 영상 ID 또는 영상 URL을 연결할 수 있어야 합니다.

영상 연결 후 YouTube Data API를 이용하여 조회수 등 공개 가능한 영상 통계를 가져올 수 있도록 합니다.

조회수, 좋아요 등 콘텐츠 반응 지표는 직접적인 금전 수익과 구분하여 성과 지표로 관리합니다.

### REQ-09-08. 실제 YouTube 수익 데이터 연동

YouTube Analytics API는 OAuth 인증을 통해 채널 소유자의 분석 데이터를 조회할 수 있으며, 별도의 금전 데이터 조회 권한을 승인받으면 estimatedRevenue 등 수익 관련 지표를 조회할 수 있습니다.

따라서 실제 YouTube 플랫폼 수익 데이터는 기술적으로 연동 가능한 데이터로 간주합니다.

다만 초기 릴리스에서는 다음 이유로 RPM 기반 예상 수익을 기본 기능으로 사용합니다.

- Google 계정 및 채널 권한 연동 없이도 서비스를 사용할 수 있도록 하기 위함
- 사용자에게 민감한 수익 데이터 권한 승인을 필수로 요구하지 않기 위함
- 외부 인증 및 API 연동 실패와 관계없이 기본적인 성과 분석을 제공하기 위함

향후 사용자가 명시적으로 OAuth 권한을 승인한 경우 실제 YouTube Analytics 수익 데이터를 선택적으로 연동할 수 있도록 확장합니다.

참고:

- [YouTube Analytics API - Reports Query](https://developers.google.com/youtube/analytics/reference/reports/query)
- [YouTube Data API - Videos](https://developers.google.com/youtube/v3/docs/videos)

### REQ-09-09. 제작비 대비 콘텐츠 가치 분석

YMS는 프로젝트와 캠페인에 투입된 제작비와 연결된 수익을 비교하여 콘텐츠가 만들어낸 비즈니스 가치를 확인할 수 있어야 합니다.

최소한 다음 정보를 조회할 수 있도록 합니다.

- 총 제작비
- 수익 유형별 금액
- 총 귀속 수익
- 제작비 대비 수익 차액
- 제작비 대비 수익 비율
- 조회수 등 콘텐츠 성과 지표

개별 영상의 조회수가 높다는 이유만으로 성공한 프로젝트로 판단하지 않으며, 직접 수익과 캠페인 전체 성과를 함께 확인할 수 있어야 합니다.

수익을 특정 프로젝트에 직접 귀속할 수 없는 경우에는 이를 임의 배분하지 않고 캠페인 또는 상위 단위의 성과로 표시합니다.

### REQ-09-10. 캠페인 성과 분석

캠페인 단위에서는 연결된 모든 영상 프로젝트의 제작비와 성과 지표를 조회하고, 캠페인에 직접 귀속된 광고·협찬·판매 등 수익을 함께 비교할 수 있어야 합니다.

이를 통해 여러 콘텐츠를 하나의 계약이나 마케팅 활동으로 제작한 경우 다음 내용을 확인할 수 있어야 합니다.

- 캠페인 전체 제작비
- 캠페인 전체 수익
- 포함된 콘텐츠 수와 진행 상태
- 콘텐츠별 조회수 및 주요 성과
- 제작비 대비 캠페인 수익성

### REQ-09-11. 외부 데이터 갱신 실패 처리

YouTube API 호출이 실패하거나 할당량 제한 등으로 데이터를 갱신할 수 없는 경우 기존에 저장된 마지막 성공 데이터를 유지합니다.

화면에서는 마지막 데이터 갱신 시각과 현재 갱신 실패 여부를 사용자가 확인할 수 있어야 합니다.

## 11. 비기능 요구사항

### NFR-01. 인증 및 접근 제어

인증이 필요한 API는 로그인한 사용자만 접근할 수 있어야 합니다.

워크스페이스 및 프로젝트 리소스는 서버에서 권한을 다시 검증해야 하며 클라이언트 화면의 노출 여부만으로 접근 권한을 제어해서는 안 됩니다.

### NFR-02. 입력값 검증과 오류 응답

클라이언트와 서버 양쪽에서 필요한 입력값을 검증합니다.

서버 API는 오류 유형을 구분할 수 있는 일관된 오류 코드와 메시지를 반환해야 합니다.

인증 만료, 권한 부족, 잘못된 입력, 존재하지 않는 리소스와 서버 오류를 구분하여 처리합니다.

### NFR-03. 금액 및 수익 계산 정확성

제작비, RPM, 예상 수익과 정산 금액은 부동소수점 오차가 발생하지 않는 자료형과 계산 방식을 사용합니다.

백엔드에서는 금액 계산에 `BigDecimal` 사용을 기본으로 합니다.

### NFR-04. 목록 데이터 조회 성능

프로젝트, 작업, 채팅, 알림 등 지속적으로 데이터가 증가하는 목록은 전체 데이터를 한 번에 반환하지 않도록 페이지네이션 또는 커서 기반 조회를 지원합니다.

### NFR-05. 외부 API 의존성 분리

YouTube API 장애 또는 미연동 상태에서도 프로젝트, 일정, 채팅, 정산 등 YMS의 핵심 업무 기능은 사용할 수 있어야 합니다.

외부 데이터는 마지막 정상 조회 결과와 갱신 상태를 구분하여 관리합니다.

### NFR-06. 동시 수정 처리

여러 사용자가 동일한 프로젝트, 작업 또는 정산 데이터를 동시에 수정할 수 있음을 고려합니다.

중요 데이터가 마지막 요청에 의해 조용히 덮어써지지 않도록 버전 관리, 낙관적 잠금 등 동시성 제어 방식을 데이터 및 API 설계 단계에서 결정합니다.

### NFR-07. 시간 정보

날짜와 일시를 명확히 구분합니다.

업로드 일시, 메시지 작성 시각, 알림 시각 등 실제 시점이 중요한 데이터는 서버에서 일관된 기준으로 저장하고 사용자 화면에서 적절한 지역 시간으로 표시합니다.

### NFR-08. 반응형 UI

주요 화면은 데스크톱과 모바일 환경에서 사용할 수 있어야 합니다.

특히 일정 확인, 알림, 채팅과 작업 상태 변경은 모바일 환경에서도 핵심 기능을 수행할 수 있어야 합니다.

## 12. 초기 릴리스 범위

초기 릴리스에서는 다음 기능을 우선 구현합니다.

1. 회원가입, 로그인 및 프로필 설정
2. 워크스페이스 생성과 멤버 초대
3. 채널 등록
4. 캠페인 생성과 프로젝트 연결
5. 프로젝트와 작업 CRUD 및 권한 제어
6. 캘린더 기반 일정 조회
7. 프로젝트 채팅과 알림
8. 대시보드 요약
9. 제작비 및 정산 관리
10. 협찬·제휴·상품 판매 등 수익 항목 수동 등록
11. YouTube 영상 조회수 연동
12. RPM 기반 YouTube 플랫폼 수익 추정
13. 프로젝트 및 캠페인 단위 제작비 대비 콘텐츠 가치 분석

실제 YouTube Analytics 금전 지표 연동과 그 외 고급 분석 기능은 초기 릴리스 이후 확장 기능으로 진행합니다.

## 13. 초기 릴리스 제외 범위

다음 기능은 초기 릴리스에서 직접 구현하지 않습니다.

- 실제 영상 파일 업로드 및 영상 편집 기능
- 작업자에게 실제 금액을 송금하는 결제 또는 계좌이체 기능
- YouTube Studio를 대체하는 채널 관리 기능
- Google OAuth를 이용한 실제 YouTube 수익 데이터 연동
- 모바일 전용 네이티브 애플리케이션

초기 버전은 영상 제작 업무의 관리와 협업, 정산을 기반으로 **콘텐츠 제작에 투입한 비용으로부터 얼마의 가치를 만들었는지 관리하는 것**에 집중합니다. 외부 매출 시스템의 완전한 자동 연동보다 수동 입력과 YouTube 기본 데이터 연동을 우선하여 실제 사용 가능한 범위를 확보하고, 이후 사용자 피드백에 따라 확장합니다.
